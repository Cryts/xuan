# 玩法方案 · 成就系统与坊市行囊

> gameplay-designer · 2026-09-20
> 依据：`tools/playtest.ts 300`、`tools/sim.ts 2400` 的输出，以及三个一次性统计脚本
> （`/tmp/bag-stats.ts`、`/tmp/bag-stats2.ts`、`/tmp/scenario-stats.ts`、`/tmp/daily-stats.ts`，共 5100 局）。
> **本文件只给方案与依据，不含任何代码改动。**

---

## 【判断】三句话

1. **成就系统不需要"设计"，需要"接线"。** 内容侧已经写好了 846 处授予点、358 个成就条目、65 个结局的解锁引用 —— 但运行时一个都不落盘、一个都不显示。**其中 357/358（99.7%）的成就名与描述可以直接从授予处派生**，一个字都不用新写。用户要的"总体的成就系统"里，**主体是已存在的、被丢掉的账**，不是新系统。
2. **行囊不是"没被用"，是"没被填"。** 实测一局净流失 **−0.92 件**物品，63.5% 的局一件都没进过手，53.8% 的局空囊收场。玩家在剧本里想翻行囊，但里面是空的 —— 18.1% 的剧本节点一件可试的东西都没有。真正让行囊像摆设的是**供给**，不是使用路径。
3. **坊市的问题不是"不能随时去"，是"换了等于没换"。** 它把灵石换成突破材料，而突破材料每局进 10.2 出 0.6，**同样没有去处**。用没有出口的资源换另一种没有出口的资源，等于什么都没发生。

## 一、【实测依据】（先看数，再看方案）

### 1.1 行囊：一局结束时到底有几件东西

| 指标 | 实测值 | 怎么测的 |
|---|---|---|
| 一局结束时行囊物品数 | **平均 0.80 件**（中位 0，p90 = 2，max 5） | 1800 局，三种玩家原型 |
| **空囊收场的局** | **53.8%** | 同上 |
| ≤2 件的局 | 93.1% | 同上 |
| 一局**入手**物品数 | **平均 0.43 件** | 1500 局，逐拍比对 `state.items.length` |
| **整局一件都没进过手的局** | **63.5%** | 同上 |
| 一局**消耗**物品数 | **平均 1.35 件**（全部来自剧本失败尝试 `consumeOne`） | 同上 |
| **净流量** | **−0.92 件/局** | 同上 |
| 带 `add_item` 的事件 | **25 / 553（4.5%）** | 扫全部事件 JSON |
| 被 `add_item` 引用过的物品 | 85 / 205 件 | 同上 |

**结论：行囊是个漏的桶。** 一局平均只进 0.43 件，剧本却平均吃掉 1.35 件。
`submitTrial` 在未命中时会 `consumeOne`（`src/core/engine.ts:1174`）——
试错要付学费是合理的，但在"一局只进 0.43 件"的供给下，学费收不起。

### 1.2 行囊在剧本里顶不顶用

| 指标 | 实测值 |
|---|---|
| 每局进入剧本 | 1.23 次（900 局） |
| 剧本节点上「可试的东西」 | **平均 1.64 件** |
| **一件可试的都没有的剧本节点** | **18.1%** |
| 破局来自行囊 | 189 / 629 = **30.0%** |
| 破局来自通用手段（探查/交涉/硬闯…） | 440 / 629 = **70.0%** |
| 行囊每次尝试的命中率 | 13.1% |
| 通用手段每次尝试的命中率 | 21.6% |

**结论：路径是通的，货架是空的。** 通用手段 70% 是好事（说明"不依赖背包也能玩"的设计成立），
但行囊 30% + 命中率 13.1% 说明：**玩家翻了行囊，多数时候翻出来的是不对的东西，或者什么都没有。**

### 1.3 灵石：不是进得少，是两头都没有出口

| 指标 | 实测值 |
|---|---|
| 每局灵石流入 | 181.7（其中斗法战后 **136.1**、事件 45.6） |
| 每局灵石流出 | **28.1** |
| 流入 : 流出 | **6.5 : 1** |
| 终局灵石 ≥300 的局 | 35.5% |
| 终局灵石 ≥500 的局 | 12.9% |
| **从不斗法的局**终局灵石 | **65**（含开局 20，全程事件只给约 45） |
| **斗法 ≥3 次的局**终局灵石 | **360** |

**结论：灵石供应是双峰的（65 / 360，5.5 倍）。** 用户说的「灵石在事件里进得太少」
**只对不斗法的人成立**；对斗法的人，灵石多到没处花。**真问题是分配双峰 + 零出口，不是总量少。**
只加 faucet 不加 sink，只会让富的更富。

同理，`rare_mat` 每局进 10.2 / 出 0.6 —— 它是**第二个没有出口的资源**。

### 1.4 日常枢纽：五项被选中的分布

500 局、**均匀随机**选（不带原型偏好，量的是菜单本身）：

| 选项 | 被选中占比 | 可用率 |
|---|---|---|
| cultivate 闭关 | 19.8% | 100% |
| roam 游历 | 21.2% | 100% |
| gather 采药 | 20.9% | 100% |
| **market 坊市** | **17.0%** | 82.0% |
| befriend 交游 | 21.1% | 100% |

每局平均 5.02 次日常节点。

**结论：均匀随机下 market 并不"无人问津"（17%）。** 它被冷落是在**原型模拟**里 ——
因为原型有偏好排序，而坊市的收益（−40 灵石 → +3 材料）在任何排序下都排在闭关/游历之后。
**这不是"玩家不选它"，是"选了不划算"。**

### 1.5 成就：内容侧写了，运行时丢了

| 指标 | 实测值 |
|---|---|
| `legacy_points` 每局产出 | 平均 41.2（中位 44） |
| **落盘情况** | **`src/ui/store.ts` 只持久化 `xuan.settings.v1` 与 `xuan.save.v1`，没有 meta 键** |
| `state.titles` 每局 | 平均 0.81 |
| `state.codex` 每局 | 平均 1.30 |
| **UI 中渲染 titles/codex 的地方** | **零处**（`grep -rn "codex\|titles" src/ui/` 无命中） |
| 内容侧的 `unlock_codex`/`unlock_title`/`meta_unlock` 授予点 | **846 处**（`unlock_codex` 316 · `unlock_title` 143 · `meta_unlock.codex` 328 · `meta_unlock.title` 59） |
| 其中**不同** ref | **358 个**（189 个 `codex_*` + 53 个 `title_*` + 116 个中文名如「不认命」「守炉人」） |
| 其中**能从授予处派生出可读名**的 | **357 / 358 = 99.7%** |
| 结局 `meta_reward.unlock` 引用 | 129 条 |
| 其中**在仓库里找不到任何定义**的 | **125 条（96.9%）** |
| 其中指向 `origin_*` 且该出身不存在的 | **64 条**（`meta/origins.json` 只有 36 个出身，全是 `origin_<族>_<变体>` 命名） |
| `rollGenesis` 的可选范围 | **全部 36 出身 × 80 天赋 × 4 缺陷，无任何门槛** |

**这是本轮最重要的发现，两条：**

**(a) 内容作者是照着一个 Meta 层写的，而那个层没建 —— 而且名字全都能派生。**
「以功抵劫」「把雷接过来」「以身承雷」这些 `title_*` / `codex_*`
**每个都挂在剧本的一个 `breakthrough` 上，而那个 breakthrough 自带 `name` 与 `cost` 文案**：

```jsonc
// src/content/scenarios/scn_mortal_owed_bolt.json
{ "id": "solve_merit_offers", "name": "以功抵劫",
  "cost": "你把这些年积的功德摊在雷下：雷绕开了你，却记住了你的味道",
  "outcome": { "effects": [ ..., { "type": "unlock_title", "ref": "title_merit_shield" } ] } }
```

实测**358 个 ref 里有 357 个能这样派生出名字**（唯一 3 个例外在 `meta/destinies.json`）。
派生规则三条：
- 剧本破局 → `breakthrough.name`（「以功抵劫」）+ `breakthrough.cost`（那句代价描写）
- 路上事件 → `narrative.title_pool[0]`（「不认命」）+ 首个 tag
- 选项效果 → 选项 `text`（「把判词认下来，每天比人多练两个时辰」）

也就是说：**成就的名字与描述早就写好了，在唯一真相源里，不需要另写一份。**
（CLAUDE.md：「能派生就不要手写」—— 358 条手写成就名会立刻腐化。）

**(b) 有一批悬挂引用，是真缺陷，先报告不改。**
125 / 129 条 `meta_reward.unlock` 指向不存在的目标；64 条指向根本不存在的出身。
按 CLAUDE.md「发现是真的缺陷，先报告再改，不许默默改绿」，我**只报告**：
这批引用现在既不会报错也不会生效，属于和 `add_item` 空操作同一类的静默失效。
`content-lint` 里应该有一条 `meta_unlock_resolvable` 闸门盯住它。

## 二、【成就系统方案】—— 「玄录」

### 2.1 设计立场（先说清楚为什么不是别的东西）

我不打算做一面奖杯墙。理由是可算的：

- **动作游戏的成就是"同一套玩法里的计数器"**（爆头 100 次）。《玄》的核心卖点是**自由度**
  （CLAUDE.md 永久规则第 1 条），计数式的成就在一个 27 拍、5–8 分钟的文字局里没有意义 ——
  玩家不会为了"用物品 50 次"再玩一局。
- **文字游戏的成就必须能被读成一句指令**：「你下次可以试试不杀一人」。
  它给的不是徽章，是**一个你没想到的玩法**。
- 参考 roguelike 的 metagame 定义（`参考/roguelike.txt`）：
  *"achieving certain goals will unlock persistent features such as the ability to select
  a new character at the start of the game or the addition of new items and monsters in the
  procedural generation of the game's levels"* —— **解锁的是"玩法空间的宽度"，不是数值。**
  这条与本作的铁律「它增加了哪一类自由度」完全同向。

所以「玄录」分五卷，四卷是**派生**的（不新增文案），只有一卷是新写的。

### 2.2 数据形状

#### (1) 新增一个条件类型 `run_fact`（唯一的引擎改动）

```ts
// src/core/types.ts
export type RunFactKey =
  | 'kills'            // 亲手取人性命（含截杀位面之子）
  | 'spared'           // 斗法后放走
  | 'duels'            // 出手次数
  | 'avoided'          // 避战次数
  | 'items_gained'     // 一局入手物品数
  | 'items_used'       // 主动用掉的物品数
  | 'daily_market'     // 去过几次坊市
  | 'scenarios_entered'
  | 'breakthroughs'    // 找到的破局通路数（一个剧本可通多条）
  | 'crits' | 'crit_fails'
  | 'hp_peak'          // 一生最重的伤势
  | 'corruption_peak'
  | 'realm_top_min'    // 最高时离绝顶几层

// Condition 联合类型里加一支
| { type: 'run_fact'; key: RunFactKey; op: CompareOp; value: number }
```

`run_fact` 在 `resolveEnding` 里结算一次，**复用现有的 `evaluate()`**（`src/core/conditions.ts`），
不新增求值器。派生来源（**能派生就不新增状态**）：

| key | 来源 | 要新增状态吗 |
|---|---|---|
| `kills` | `state.flags` 里 `slew_*` / `destiny_slain_*` 的条数 | 否 |
| `avoided` | `state.flags` 里 `avoided_*` 的条数 | 否 |
| `crits` / `crit_fails` | `state.history[].band` | 否 |
| `scenarios_entered` | `state.completed_scenarios` | 否 |
| `daily_market` | `state.history[].option_id === '__daily__'` 计数 | 否 |
| `hp_peak` / `corruption_peak` | 在 `advanceNode` 这个单一入口记录峰值 | 是（2 个标量） |
| `spared` | `submitDuelAftermath` 的 `kill === false` 分支 | 是（1 个标量） |
| `duels` | `submitDuelStance` | 是（1 个标量） |
| `items_gained` / `items_used` | `mergeDelta` 的 `add_item` 分支 / `useItem` | 是（2 个标量） |
| `breakthroughs` | `finishScenario` 里 `run.solved` 已有，只差记下来 | 是（1 个 `string[]`） |

即：**新增 `state.run_facts` 结构，但 5 个字段是派生、6 个是计数器。**
`run_facts` 缺失时（老存档续玩）**不能静默填 0** —— 否则「手下留人」会白送。
必须与 `readSave` 的容错一起处理。

#### (2) 新内容文件 `src/content/meta/achievements.json`（约 24 条，这是唯一新写的文案）

```jsonc
{
  "id": "ach_no_kill",
  "name": "手下留人",
  "hint": "一世不曾亲手取人性命。",          // 未解锁时显示 —— 给方向，不给解法
  "group": "path",                            // path 道途 / deed 事迹
  "tier": "A",
  "requires": { "type": "all", "of": [
    { "type": "run_fact", "key": "kills", "op": "==", "value": 0 },
    { "type": "run_fact", "key": "realm_top_min", "op": "<=", "value": 6 }
  ]},
  "reward": { "legacy_points": 20, "unlock_trait": "trait_xxx" },
  "secret": false
}
```

`requires` 就是现有的 `Condition` —— **不发明新的条件语言**，
这样 `content-lint` 现有的 `condition_reachable` / `scenario_solvable` 那套校验能直接复用。

**闸门（加功能必须同时加闸门）**：
- `run_fact_known`：`run_fact.key` 必须在 `RUN_FACT_KEYS` 白名单里，否则 error。
- `achievement_reachable`：模拟 2000 局，每条成就至少解锁一次，否则报"疑似不可达"
  （这个项目已经吃过"剧本属性门槛不可达"的亏，闸门是现成的范式）。
- `meta_unlock_resolvable`（**新，且当前就会 fail**）：每条 `meta_reward.unlock` /
  `meta_unlock` 的目标必须在仓库里有定义。当前 125 条会打回 —— 这正是它该做的事。

#### (3) 持久化记录（**只能待在 UI 层**）

core 必须保持零浏览器 API（`npm run check:core` 强制），
所以 core 只出一个**纯函数** `summarizeRun(state, content): RunRecord`，
落盘由 `src/ui/store.ts` 负责：

```ts
// src/ui/store.ts —— localStorage key: "xuan.meta.v1"
export interface XuanRecord {
  v: 1
  runs: number
  legacy_total: number                        // 累计轮回点
  endings_seen: Record<string, { n: number; best_stars: number }>
  breakthroughs: string[]                     // "scn_id:bt_id"，已找到的破局通路
  achievements: string[]                      // 已解的道途成就
  scenarios_seen: string[]
  events_seen: string[]                       // 见闻计数用
  marks: Record<string, string[]>             // 已买断的解锁：{ origins, traits, flaws, items }
}
```

### 2.3 触发条件

三条路径，各有各的时机 —— **这个时机差别本身就是设计**：

| 卷 | 触发 | 时机 | 为什么是这个时机 |
|---|---|---|---|
| **破局录** | `finishScenario` 里 `run.solved` 已算出 | **局内实时**，解锁时弹一条 `RevealOverlay` | 「你找到了五条路里的一条」——这是全局最爽的一刻，必须当场说 |
| **命册** | `resolveEnding` | **结局画面** | 结局是唯一该在结束时揭晓的东西 |
| **道途** | `advanceNode` 后逐拍求值 | **局内实时**，可当场弹 | 「你这一世已是不杀之人」——要让玩家在**过程中**知道自己正在完成它 |
| **见闻（事迹）** | `unlock_codex` / `unlock_title` / `meta_unlock` | **局内实时**，可当场弹 | 358 条，按体系包分卷；名字从授予处派生 |
| **轮回** | `legacy_points` 累加 | 结局画面 | 与现有 `EndingScreen` 的「轮回点」一行接上 |

### 2.4 界面呈现

**「玄录」是一块全屏板**（复用 `HeavenBoard` 天机榜的形态 —— 本项目已有这个 idiom），
从四处可达：**标题画面**、**结局画面**、**日常枢纽**、**行囊**。

#### 命册（65 条 · 全派生）

```
飞升 · 独上                         ★★★★☆  见过 2 次
  天门开，无人送                     「离绝顶四层以内，身边一个盟友都没有」
────────────────────────────────────
飞升 · ？？？                       未录
  离绝顶四层以内，身上背着六十年杀孽      ← 由 requires 的 Condition 树派生成人话
```

已见的给 `title_pool[0]`（已存在）+ 最高星；未见的给分类 + **一行由 `requires` 派生的提示**。

#### 破局录（18 剧本 × 94 条通路 · 全派生）**—— 这一卷是钩子主体**

```
该落的雷                                       已找到 1 / 6
  ✓ 以身承雷    你一寸不动地受完了，皮肉焦了一层，骨头里却多了点东西
  ✓ 以功抵劫    你把这些年积的功德摊在雷下：雷绕开了你，却记住了你的味道
  · 散功        你把一身本事散出去当筏子，雷落了空——散出去的那些，回不来了
  · ？？？      隐藏通路
```

名字与描述**全部来自 `breakthrough.name` / `breakthrough.cost`**，一个字都不用新写。
**不给解法条件** —— 只给"有这么一条路"和它的代价，让玩家自己想。

实测：每局平均破局 **0.64 次**，总通路 **94 条**。
`sim.ts` 的 300 局试玩里 18 个剧本全部触发过 —— **这个集合是可达的，不是画饼。**

#### 道途（24 条 · 新写）

```
○ 手下留人      一世不曾亲手取人性命。              未解
✓ 散尽家财      灵石从未在手里过夜。                已解 · 得 20 点

```

#### 事迹（358 条 · 全派生）

按体系包分卷，每条一行「名字 + 出处」：

```
青冥仙途 · 该落的雷
  ✓ 以身承雷      你一寸不动地受完了，皮肉焦了一层，骨头里却多了点东西
  ✓ 以功抵劫      你把这些年积的功德摊在雷下：雷绕开了你，却记住了你的味道
  · 散功          你把一身本事散出去当筏子，雷落了空——散出去的那些，回不来了
```

**名字与描述 100% 派生**（`breakthrough.name` / `narrative.title_pool[0]` / 选项 `text`），
**不逐条手写**。全库 358 条，实测 300 局能覆盖 498/553 个事件 —— 这是一个真实可达的收藏集。

#### 轮回

`legacy_total` 与一个**买断式**解锁树（见 2.5）。

### 2.5 解锁什么 —— 奖励必须是"宽度"，不是"高度"

**轮回点的唯一用途：买断式解锁，一次性，不可重复购买，不加任何数值。**

| 可买 | 例子 | 增加的自由度 |
|---|---|---|
| 新出身 | 从 36 → 48 | 开局处境的选择变多 |
| 新天赋 | 从 80 → 100 | 构筑变多 |
| 新缺陷 | 从 4 → 10 | **自选难度**（缺陷带补偿点，这是本作已有的机制） |
| 新起始物品 | 稀有品入开局池 | 开局手牌变多 |

**明确不做**：不卖属性点、不卖修为、不卖"下一局更强"。
理由有两条，一条是设计、一条是工程：
1. 与「任何新增功能必须回答它增加了哪一类自由度」冲突 —— 数值提升不增加自由度。
2. **会把 2400 局平衡标定作废。** 现状 `sim.ts` 是 8/9 通过，
   而**道陨率 40.4% 已经贴着 40% 的上限**。任何"下一局更强"的累积都会把它推过线。

### 2.6 为什么玩家会想再来一局（这是本方案的核心，单独说）

四个可数的钩子，每个都指向一个具体的"我还没……"：

1. **「94 条破局路，你找到了 1 条。」**
   实测每局破局 0.64 次 → 平均 147 局才能集齐。
   但钩子不在"集齐"，在**下一条就在眼前**：同一个剧本你刚刚进去过，
   玄录告诉你它还有五条路，且**给了你三条的名字**（「散功」——散掉一身修为换命）。
   玩家当场就能想出"下次我试试散功"。**这是本作最匹配的动机形态 —— 智性破局。**

2. **「65 个结局，你见过 3 个。另外 62 个的条件里，有 4 条提示。」**
   实测 300 局只出现 12 个分类，4 个分类一次都没出现
   （走火入魔·转世再来·屠尽仇寇·特殊彩蛋）。这些是**已经写好但没人见过**的内容。
   同一卷里还有 **358 条事迹**（实测 300 局覆盖 498/553 个事件，是真实可达的收藏集）。

3. **「这一世我要试试不杀一人。」**
   这条最重要：**开局前就宣布的成就改变的是整整 27 拍的决策**；
   结束后才发现的成就只是一张收据。所以玄录里已解锁的道途可以**在转世画面勾选**
   —— 勾上之后它是你这一局的自定约束，达成后记账。
   **这是新增的一类自由度：玩法的自由度，而不只是剧情的自由度。**

4. **「你已经 7 局没有新的东西入录了。」**
   一个诚实的负反馈。它不做惩罚，只是让"重复"变得可见 ——
   对应 `参考/grinding.txt` 里那句 *"the most effective path to victory should also be the most fun"*：
   当最优路径变成重复劳动时，把重复**显示出来**，比偷偷加数值惩罚更诚实。

**反过来说，什么会让它失败**（我在【代价】里会再展开）：
如果玄录变成一张"必须刷"的清单，它就退化成了 grind。缓解是**不给数值奖励 + 不剧透解法**。

## 三、【商店与行囊方案】

### 3.1 先修供给：让物品真的进得来

这是问题 2 的**主体**，坊市只是手段之一。四条，按性价比排序：

**(a) 提高 `add_item` 的事件密度。** 当前 25/553 事件（4.5%）带 `add_item`。
目标：**≥ 15%**（约 83 个事件）。这是内容侧的活，不需要引擎改动。

**(b) 「采药」与「坊市」要产出物品，不只是材料。**
现状 `dailyActions` 里五个选项**没有任何一个产生物品**（`src/core/engine.ts:1646-1719`）。
`gather` 给 `rare_mat`（而 rare_mat 没有出口），`market` 用灵石换 `rare_mat`。
`gather` 应当有概率给**带 `疗伤` / `解毒` / `续命` 标签的物品** —— 这是"日常物品从哪来"最自然的地方。

**(c) 剧本破局要给物品，不只是数值。**
CLAUDE.md 已有这条（「前面的选项与成败必须给玩家剧本相关的道具，且成败给的东西不同」），
但实测显示它没有落到 `add_item` 上：剧本里的破局收益几乎全是 `add_var`。
**这条应该进 `content-lint` 当闸门。**

**(d) 每次进剧本时给一件"入场赠品"。**
剧本已有 `leadup_motifs` 机制（剧本登场前插 2~4 拍铺垫事件）。
让这些铺垫事件**必带 `add_item`** —— 这样"玩家带着一路攒下的东西走进剧本"
（`src/core/types.ts:268` 的注释原话）才真的成立。实测现在进剧本时手里平均只有 1.64 件可试之物。

### 3.2 坊市：形态

**用户原话是"商店等游戏中常有的地点应该作为一个可以随时去的选项"。**

**我的答复分两半：**
- 「随时能去」**成立**，而且应该做到 —— 但实现方式是**必现且可规划**，不是"任何时刻能点开"。
- 「随时能**买**」**不成立**，我反对。理由是可算的：

> 一局只有 **27 拍**，其中日常 **5.02 拍**。**时间是本作唯一的稀缺资源**，
> 灵石、材料、伤势全都是流量。一个不占拍的商店 = 免费的资源转换 = **严格支配"把灵石留着"**，
> 而且它绕开了本作唯一的时间压力。`sim.ts` 的支配性检测（2400 局 ±2.3%）会立刻抓到它。

**推荐形态**（与剧本入场同一套 idiom，`submitScenarioEntry` 已经跑通了这个模式）：

- **触发**：每局第 3、9、15、21 拍**必现**一次（`node_index % 6 === 3`），**不是随机**。
  玩家能规划"我攒到第 15 拍去买"。
- **呈现**：一个带三行氛围描写的地点，两条路 —— 「进去 / 路过」。
  **"随时能去"实现为"你知道它一定在、且你能选择去不去"**，
  这比"任何时刻都能点开"更符合一个文字游戏的质感，也不破坏时间压力。
- **代价**：进店耗一拍。**进店后可以买任意多笔**（一次采购），不再二次收费。
- 一局最多进店 4 次（27 拍 / 6）—— **硬上限，不需要额外的防刷规则兜底。**

**与日常枢纽的关系（明确分工，不同栏、不同价）：**

| | 管什么 | 频率 | 性质 |
|---|---|---|---|
| **日常枢纽** | **时间分配**（闭关/游历/采药/交游） | 每 4 拍一次 | 大决策，量级是"这三个月" |
| **坊市** | **资源转换**（以物易物、以灵石易物） | 每 6 拍一次，必现 | 小决策，量级是"这一趟" |

**并且：把 `market` 从 `dailyActions` 里去掉。**
把一个"买一瓶丹"塞进"闭关三个月 / 出门游历"的菜单里，两件事量级不对等 ——
实测就是这个后果：原型模拟里 `market` 与 `gather` 从不会被选中，因为闭关和游历总是更划算。

> ⚠️ 这一条涉及日常菜单从五选一变四选一，**归 `systems-designer` 会签**。
> 我给出的是理由与实测，不是决定。

**真正"随时"的那一半已经存在了：** `useItem` 不推进节点（`src/core/engine.ts:2029`），
日常物品任何时候都能用。用户要的"随时"在**用**这一侧已经成立，
缺的是**买**这一侧 —— 而买必须占拍。

### 3.3 坊市：卖什么

- **主要卖物品**（`add_item`），不是材料。这是直接修"行囊是摆设"。
- 每次上架 **3~5 件**，按 `state.pack_id` 与 `realm_idx` 加权抽取。
- **卖出**：按品阶给低价（买价的 40%），让一囊没用的 `key` 类有去处。
- **硬约束：货架不按"当前剧本所需的功能标签"抽取。**
  剧本的设计前提是"关联性解法"（CLAUDE.md），如果坊市能定向买到答案，
  18 个剧本全部退化成"攒钱买钥匙"。**货架按体系包抽，不按需求抽。**

### 3.4 经济上的防刷设计（四条，都可算）

1. **占拍** —— 一局最多进店 4 次。**这是主防线，其余三条是补充。**
2. **同局内同类物品第 n 件价格 ×(1 + 0.35n)**（掌柜看出你急用）。
   单局内批发自我限制，让"斗法致富"不能直接变成"买空货架"。
3. **价格随境界走**：`price = base × (1 + realm_idx × 0.6)`。
   **这条是被实测逼出来的**：终局灵石是 65 vs 360 的双峰分布，
   固定价格必然要么对穷玩家无意义、要么对富玩家是白送。用户已提过这一条，数据支持它。
4. **卖价 = 买价 40%** —— 从根上堵死"买了再卖"的套利。

**不改的部分**：`rare_mat` 每局进 10.2 / 出 0.6，是第二个没有出口的资源。
**它的去处归 `systems-designer`**（坊市卖材料只是把问题挪了个地方）。
我只标出来，不给方案。

### 3.5 闸门（加功能必须同时加闸门）

| 规则 | 判据 | 现状读数 |
|---|---|---|
| `item_flow_positive` | 每局入手物品 **≥ 2.0** | **0.43** ✗ |
| `bag_not_empty` | 终局空囊率 **≤ 20%** | **53.8%** ✗ |
| `trial_always_available` | 剧本节点可试件数为 0 的比例 **≤ 5%** | **18.1%** ✗ |
| `market_stock_daily` | 货架每日至少 2 件带 `DAILY_AFFORDANCES` 标签 | 新 |
| `market_stock_reachable` | 模拟 500 局，货架出现过的物品 id ≥ 全库一半 | 新 |
| `meta_unlock_resolvable` | 所有 unlock ref 有定义 | **125 条悬挂** ✗ |
| `achievement_reachable` | 2000 局内每条成就至少解锁一次 | 新 |

前三条直接量"行囊不再是摆设"，是非要看数不可的部分。

## 四、【代价】这些改动会让什么变差

按严重程度排：

1. **道陨率会越过 40% 的红线，`sim.ts` 的标定要重跑。**
   现状 **40.4%**，阈值 **≤40%**，已经贴线。物品变多 → 破局变多 → 战力变高 →
   道陨率下降是好事，但**支配性比值也一定会动**（2400 局 ±2.3%）。
   **这是最实在的代价：一份已经标定好的 2400 局平衡报告会部分作废，必须重跑。**

2. **成就会把"随机漫游"变成"待办清单"，压缩纯探索的乐趣。**
   一旦玄录告诉你"还有 93 条没录"，就会有人去刷它；
   而刷的方式是**重复同一个剧本试不同通路** —— 这正是 `参考/grinding.txt` 说的
   "重复劳动变成惩罚"的典型场景。
   **缓解**：破局录**只给名字与代价，不给解法条件**（不剧透）；
   成就奖励是**解锁新玩法**而非数值，让动机停在"想试试"而不是"必须刷"。

3. **坊市卖物品会削弱剧本的"关联性解法"张力。**
   玩家可以靠买买买绕过一部分"你得先在某处拿到某物"的设计。
   **缓解**：货架按体系包抽而不按剧本需求抽（3.3 的硬约束）+ 单局涨价。

4. **去掉日常的 `market` 会让稳健型玩家少一个选项。**
   实测它在均匀随机下被选 17%，不是无人问津。
   去掉它必须补一个同量级的选项，否则日常从五选一变成四选一，**菜单变薄**。

5. **持久化不是"加个 localStorage"那么轻。**
   `xuan.meta.v1` 一旦上线就有迁移负担；而本作部署在 GitHub Pages，
   **清一次浏览器缓存全没**。需要一个诚实的提示，或者导出/导入。
   而且这是**首次在 UI 层引入跨局状态** —— 现在 UI 层只有「设置」与「当前存档」两件事。

6. **`run_facts` 会扩大 `GameState`，并且必须进存档序列化。**
   老存档续玩时字段缺失**不能静默填 0** —— 否则「手下留人」会白送。
   这与项目已有的"先报告再改"纪律直接相关。

7. **核心纯度约束**：玄录的落盘只能在 `src/ui/store.ts`，
   core 里只能有纯函数 `summarizeRun(state, content): RunRecord`（`npm run check:core` 会看着）。
   这会往 UI 层加一层状态管理层。

8. **`run_fact` 求值有性能顾虑（很小但要说）**：
   若在 `advanceNode` 后逐拍求值 24 条成就 × 27 拍 = 648 次条件求值，可忽略；
   但 2400 局 × 3 原型 × 648 = 470 万次，会让 `sim.ts` 变慢。
   **建议：`sim.ts` 里可关闭成就求值** —— 但那样闸门就看不见它了。
   取舍留给 `engineer`。

## 五、对用户要求的异议（我是专家，不是执行手）

### 异议 1：「灵石在事件里进得太少」—— 只对一半人成立

实测：**从不斗法的局终局 65，斗法 ≥3 次的局终局 360**，差 5.5 倍。
真问题是**分配双峰 + 零出口**（进 181.7 / 出 28.1 = 6.5:1），不是总量少。
**只加 faucet 不加 sink，只会让富的更富**，而穷玩家依然没得花。
建议把这条的处置权交给 `systems-designer`，我这边只提供坊市这个 sink。

### 异议 2：「商店应该作为一个可以随时去的选项」—— 一半同意

**「随时能去」我同意，并且我的方案比"随时"更强：必现、可规划、你知道它在哪。**
**「随时能买」我反对** —— 时间是本作唯一的稀缺资源，不占拍的商店是严格支配策略，
会被 2400 局的支配性检测抓到（见 3.2）。

### 异议 3（最重要）：「需要有总体的成就系统」—— 主体不是"设计"，是"接线"

实测显示成就系统在内容侧**已经写好了**：
846 处授予点、358 个成就条目（99.7% 可派生名）、129 条结局解锁、94 条自带走姓名与描述的破局通路。
**缺的是运行时的落盘与显示 —— 这是一个缺陷，不是一个设计空白。**

所以我建议这一轮的工作量分配是：

| 做什么 | 占比 | 性质 |
|---|---|---|
| 落盘 + 显示已存在的 846 处授予点、94 条破局通路、65 个结局 | **~70%** | **修缺陷** |
| 新写 24 条道途成就 + `run_fact` 条件类型 | ~20% | 增量设计 |
| 修 125 条悬挂引用 | ~10% | **修缺陷（先报告，见 1.5b）** |

**如果只做"新设计一套成就"而不接线，会做出第二套同样不落盘的东西** ——
这个项目已经有过多次"所有测试全绿但功能是死的"，我希望这一轮不要再加一个。

### 异议 4：行囊的问题被误诊了

用户说"行囊和摆设一样，基本不会增加物品"—— **这个观察是对的**，
但**因果是反的**：不是"行囊没用所以不增加物品"，
是**"不增加物品所以行囊没用"**。
实测玩家在剧本里 30% 的破局靠行囊、通用手段只占 70%，
说明路径是通的，只是货架是空的（18.1% 的剧本节点无物可试）。
**所以第一优先级是把 `add_item` 的密度从 4.5% 提到 15%，坊市是第二位。**

1. **先接线，再设计。** 落盘 `legacy_points` / `titles` / `codex` / 破局通路（一个 `summarizeRun` 纯函数 + 一个 localStorage 键），

3. **`add_item` 密度是内容侧的活**，交付给能批量生产事件的一方，闸门用 §3.5 的前三条。
4. **坊市与「日常去掉 market」两项需要 `systems-designer` 会签**再动手。
5. **改完必须重跑 `npx tsx tools/sim.ts 2400`**，重点看道陨率（现状 40.4%，阈值 ≤40%）与
   支配性比值（现状 17.8% ± 2.4%）。按 CLAUDE.md：读数落在噪声里就**明说测不准**。

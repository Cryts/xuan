## 零、三句话结论

| 题 | 一句话判断 |
|---|---|
| 一 · 行囊 | 不是"行囊没做"，是**入场抉择那一拍漏传了 `onBag`**，全流程只有这一拍行囊不可点；但补上按钮只解决一半 —— 入场页还缺「这一局认什么」，玩家看得见自己有什么、看不见**要什么**，照样是盲选。 |

## 一、行囊：剧本跳出来时看不见自己有什么

### 1.1 现状（读代码得到，非推测）

**根因是一处漏传的 prop。** 全流程有三个界面渲染顶栏：

| 界面 | 位置 | 传 `onBag`？ | 行囊形态 |
|---|---|---|---|
| 事件页 | `EventScreen.tsx:97-103` | ✅ 有（`:102`） | 可点按钮 |
| 剧本内 | `ScenarioScreen.tsx:99-106` | ✅ 有（`:105`） | 可点按钮 + 底部「以物试之」`ScenarioScreen.tsx:257-268` |
| **入场抉择** | `ScenarioScreen.tsx:362-368` | ❌ **没有** | **只显示件数，不可点** |

`StatusBar` 在拿不到 `onBag` 时走 `bagStatic` 分支（`StatusBar.tsx:296-308`）——渲染成一个 `<span>` 而不是 `<button>`：

```
{onBag ? (
  <button className={s.bag} onClick={onBag} aria-label={`行囊 · ${bagCount} 件`}> … </button>
) : (
  <span className={s.bagStatic}> … </span>      // ← 入场抉择走的是这一支
)}
```

而"剧本跳出来"那一拍，正是 `engine.ts:1358` 的 `buildEntryPresentation()` 产出的入场态，界面上由 `ScenarioScreen` 的 `EntryView`（`ScenarioScreen.tsx:340-432`）渲染。**所以玩家被要求做"进不进"的决定，却在这一刻失去了查看自己有什么的能力。** 这不是设计取舍，是缺陷。

**第二个缺陷（更根本，补按钮补不掉）：入场页只给明规则，不给破局条件。**

`EntryView` 只渲染 `entry.rules_stated`（`ScenarioScreen.tsx:388-400`），而 `ScenarioEntry` 这个类型里根本没有 breakthroughs（`types.ts:785-792`：只有 `scenario_id / name / lines / rules_stated / span`）。

于是入场页给玩家的信息是：

```
┌────────────────────────────────────────────┐
│  《剧名》              约 N 刻 · 不入亦可    │
│  过渡句 / 入场正文                           │
│  ┌ 此处明面上的规矩 ──────────────────────┐ │
│  │ 一 …      二 …      三 …               │ │
│  └────────────────────────────────────────┘ │
│  进去，才知道隐在明面之下的那几条；绕开，…    │
├────────────────────────────────────────────┤
│  [ 进 去 ]            [ 绕 开 ]             │
└────────────────────────────────────────────┘
        ↑ 玩家在这里要决定"我用什么破局"
          但屏幕上：没有破局条件，没有行囊
```

**要命的是数据其实已经在手边。** `pres.scenario` 就带着 breakthroughs（`types.ts:686-694`），`scenarioOf(content, id)`（`text.ts:310-312`）能取到完整 `Condition[]`，而 `unmetText()`（`text.ts:299-307`）**已经能把条件翻成"还差什么"**——剧本内界面正在用同一套（`ScenarioScreen.tsx:202-219`）。入场页要用，不需要动引擎一行。

我数了一下剧本破局条件实际用到的条件类型（扫 `src/content/scenarios/*.json`）：

```
attr 79 · var 44 · any 45 · known_rule 43 · affix_count 32 · affordance 31
relation 20 · solved_any_of 18 · realm_idx 9 · flag 8 · not 6 · item 2 …
```

**属性门槛是最大的一类，物事之能只占一小部分。** 所以入场页该给的不是"你有几件东西"，而是「**这一局会考哪几类，你各有多少**」。

### 1.2 判断

三条，按优先级：

1. **必改（缺陷）**：`EntryView` 的 `StatusBar` 补 `onBag`。这是一行的事，但它只让玩家"能看"。
2. **真解（设计）**：入场页要有一条**常驻的「这一局认什么」简报**，把破局条件按**需求类别**聚合，并对每一类标出"你够 / 你缺"。这才是"用什么破局"的决策依据。
3. **形态（体验）**：现有的 `BagSheet` 是**模态底部抽屉**（`theme.css:876-892`：`position:fixed; bottom:0; max-height:84dvh`，配 `.x-mask` 遮罩）。在决策时刻，"查看"不该等于"离开决策面"。所以：
   - **默认形态**：常驻的**标签条**（非模态、不遮选项、零点击可见）；
   - **展开形态**：点某个标签 → **原地手风琴**展开该类物事（仍在页内）；
   - **完整形态**：点「翻全囊」→ 才开模态抽屉（此时玩家已决定要看全，模态是可接受的）。

   理由：破局条件认的是**功能标签**而不是某件特定物事——`BagPanel.tsx:257-260` 和 `TrialPanel.tsx` 的注释都写明了这一点。所以**决策时刻该显示的是标签的覆盖情况，不是物品清单**。清单是"确认"用的，标签是"决策"用的。

**交互路径**

```
节点推进 → 剧本触发（pending_scenario 落库）
   → 界面渲染 EntryView
   → 【零点击】顶栏行囊件数可点 + 「这一局会认什么」+「囊中所有」标签条已在屏幕上
   → 想细看：点标签 → 原地展开该标签下的物事（不离开决策面）
   → 想全看：点「翻全囊」→ BagSheet 模态抽屉（可随手用的还能直接用）
   → 决定：[ 进 去 ] / [ 绕 开 ]
```

**边界情况（必须一起做，否则又是"结构齐备内容是空的"）**

- **空囊**：标签条不整条消失，要留一句「囊中无物 —— 这一局你只能靠手段与静观」。留白会让玩家以为是没加载出来。
- **一个标签都没有**：同上，且「这一局会认什么」那一栏要明说"这一局不考物事，考的是别的"。
- **标签覆盖为 0**：用中性灰显示「你 无」，**不要用红色警示** —— 缺一件物事不等于死路，破局条件常是多条 `any` 并联（`any 45` 次，仅次于 `attr`）。

### 1.4 依据

**引用的资料**

1. Don Norman, *Signifiers, not affordances*（ACM Interactions 15(6), 2008）— https://jnd.org/signifiers-not-affordances/
   > "People need some way of understanding the product or service, some sign of **what it is for, what is happening, and what the alternative actions are**. People search for clues, for any sign that might help them cope and understand. It is the sign that is importance… Designers need to provide these clues."

   套到本题：入场页给了"这是什么"（剧名、明规则），没给"**我有什么**"和"**替代方案长什么样**"。玩家在找线索，界面没给。

2. Wikipedia, *Slay the Spire*（Design 一节，引自对 Anthony Giovannetti 的访谈）— https://en.wikipedia.org/wiki/Slay_the_Spire
   > "…they discovered through playtesters that **having the numbers available was more engaging, did not require the player to have to memorize what each symbol meant, and enabled players to create new strategies**."

   Mega Crit 一开始也刻意不给数字，只给图标区间 —— 玩测打了回来。**"怕玩家信息过载"是个经常站不住的假设。** 这正是"行囊不该藏"的外部佐证。（注意：这条**不**等于本作该公开判定成功率，见 §4.2。）

3. Wikipedia, *Into the Breach*（Gameplay）— https://en.wikipedia.org/wiki/Into_the_Breach
   > "**The player is shown the direction of the Vek unit's intended attack** and information on the number of moves the Vek unit is able to take and its remaining health **are available on screen**."

   预告系统被公认为该作清晰度的来源：把"接下来会发生什么"摆在决定之前。对应本作 = 把"这一局会考什么"摆在"进不进"之前。

4. WCAG 2.1 SC 1.4.3 Contrast (Minimum) — https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html
   > "The visual presentation of text and images of text has a contrast ratio of at least **4.5:1**… Large-scale text and images of large-scale text have a contrast ratio of at least **3:1**"

   用于 §1.5 的验收判据（标签条是新文字，必须过 4.5:1）。

### 1.5 验收

1. **可点性**：在入场页能**一次点击**打开行囊并看到全部物事（现在是零次可点）。检查方式：`ScenarioScreen.tsx` 的 `EntryView` 里 `<StatusBar>` 有 `onBag`；或用 testing-library 对入场态渲染后 `getByRole('button', {name: /行囊/})` 能取到。
2. **不遮选项**：标签条展开时，`[进去]` / `[绕开]` 两个按钮仍在视口内且可点。判据：展开前后按钮的 `getBoundingClientRect().top` 不被遮挡（`document.elementFromPoint` 落在按钮上）。**这条比第一条重要** —— 模态抽屉也满足第 1 条，但它让玩家"看的时候不能选"。
3. **信息对得上**：入场页「这一局会认什么」列出的类别，与进局后「破局条件组」列出的条目**同源**。判据：两边都由 `scenarioOf(content, id).breakthroughs[].conditions` 派生；改一条条件，入场页与剧本内**同时**变。若入场页是手写的，这条必挂。
4. **对比度**：标签条文字对底色的对比度 ≥ 4.5:1。判据：新文字用 `--t2` 以上（实测 `--t3` 对 `--ink-2` = 5.91 ✅，`--t4` = 3.19 ❌ 不达标，见 §4.1 实测表）。
5. **零点击可见**：不点任何东西，屏幕上就能看到"我有几件、覆盖哪几个标签"。这条防的是"补了一个按钮就算修好了"。

### 1.6 代价

- 入场页会**变长**，多两栏。剧本触发时玩家本来在读正文，多出来的信息可能被跳过。缓解：标签条**压在 footer 上方**（拇指区），「这一局会认什么」**默认收起成一行摘要**（"这一局考四类，你足其一"），点开才展开。
- 常驻标签条会把"我有什么"变成一个持续存在的读数，**削弱了"翻行囊"这个动作的仪式感**。可接受 —— 决策时刻的清晰度比仪式感值钱。
- 「这一局会认什么」若做得太直白，会**削弱剧本的推理乐趣**。这是真风险，需要 `gameplay-designer` 拍板粒度：我建议**只给类别与够/缺，不给具体数值门槛**（"道行需不低于第几境 · 你差一点"，而不是"需不低于第几境（今第几境）"）。这与本作"不给精确成功率"的取向一致。

## 二、结局归因：为什么是这个结局、哪一步走岔了

### 2.1 现状

结局页 `EndingScreen.tsx` 现在给玩家的全部"复盘"是这一段（`:37-52`）：

```ts
const out = [
  `出身体系：${packName(...)}`, `终至境界：${realmName(...)}`,
  `战力指数：${state.power_index}`, `因果债务：${state.vars.debt}`,
  `功德：${state.vars.karma}`, `心魔：${state.vars.corruption}`,
  `历事：${state.node_index} 节`, `破去的剧本：${state.completed_scenarios.length} 局`,
]
```

**这全是 tally（我做了什么），没有一条因果（所以我落到这里）。** 玩家看到的是成绩单，不是复盘。

而**归因所需的全部数据都已经存在**：

- **每个结局自带条件树**：`Ending.requires?: Condition`（`types.ts:420`）。65 个结局，16 个 `category`（飞升 / 道陨 / 因果清算 / 走火入魔 / 沦为他人道果 / 苟道长寿…）。
  例：`{"id":"end_ascend_hollow", "category":"飞升", "requires":{"type":"all","of":[{"type":"realm_top","value":4},{"type":"var","key":"corruption","op":">=","value":60}]}}`
   —— 这个结局的名字叫「残神登天」：**飞升了，但心魔缠身**。玩家凭什么知道自己为什么飞升成了残神？就凭这条 `all[realm_top>=4, corruption>=60]`。
- **`fitScore` 已经在逐条打分**（`engine.ts:2605-2687`）：数值条件算"距离"、`realm_top`/`realm_idx` 是硬门槛（`engine.ts:2655-2676`）、`all` 走"短板主导"（`weakest*0.6 + mean*0.4`，`engine.ts:2637-2643`）。
- **落选者也算了分**：`resolveEnding` 里 `scored` 是全库排序（`engine.ts:2715-2717`），`near` 是"差 0.15 以内的一批"（`:2721`）。**这些恰好就是"差一点的那个结局"。**
- **每一手都记了账**：`HistoryEntry`（`types.ts:554-566`）有 `node_index / event_id / option_id / intent / band / delta`，`delta` 是**逐变量的真实增减**（`engine.ts:1077-1085`）。
- **条件→人话已经写好**：`shortfall()`（`text.ts:227-296`）产出"根骨需不低于五十八（今四十三）"这种句子。

**结论：归因界面可以零手写文案。** 这是 CLAUDE.md「能派生就不要手写」的直接应用 —— 65 个结局 × 若干条件，手写必然腐化，而**归因写错比不写更糟**（玩家会照着错的复盘去改下一世）。

**但有一个真缺口必须先说：**

- `HistoryEntry.breakthrough_id?: string`（`types.ts:564`）**声明了，从未被写入过**（全仓 grep，只有类型定义这一处命中）。所以"哪一手破了哪个条件组"这条链**现在是断的**。要做完整的归因，得先在 `engine.ts` 里把它写上（破局那一步的 `history` 记录）。
- `play/entry`（进/绕开）**完全不写 history**：看 `submitScenarioEntry`（`engine.ts:2053-2088`），进和绕开两条分支都不 push history。所以"你绕开过几处"在 `history` 里查不到。
- **顺带查到一个显示错误**：`EndingScreen.tsx:48` 写「破去的剧本：N 局」，取的是 `state.completed_scenarios.length`。而 `completed_scenarios` **同时包含破局与绕开**（破局：`engine.ts:1235`；绕开：`engine.ts:2083`）。**玩家绕开的每一处都被算成"破去的"** —— 这是"提示与行为对不上"那一类，数字偏大且偏得没道理。

### 2.2 判断

**要做，而且是三个层次，不是一段总结。**

- 层次一（**为什么是这个**）：把中选结局的 `requires` 摊开，逐条标成/未成 + 你的实际值。
- 层次二（**差一点的是哪个**）：拿 `scored` 的次席，指出**哪一条条件把它挡掉了**。这一层直接回答用户问的"我哪一步走岔了"。
- 层次三（**哪几手推的**）：从 `history` 里筛出对**该结局关键变量**影响最大的那几手，列出"第几节 · 你选了哪一手 · 它动了什么"。

### 2.3 ⚠️ 我要直接说的一条：用户的要求里有一步是错的

> 用户原话：「结局和选项应该有关联才对（最后应该有总结告诉玩家为什么会有这个结局，**哪些选项导致的**）」

**"哪些选项导致的"这个提法，在本作的引擎里多数时候不成立。**

看 `resolveEnding`（`engine.ts:2700-2750`）：结局是**按贴合度排序 + 在 0.15 邻域内带权重随机**挑出来的（`:2715-2727`）。也就是说——

- 玩家拿到「残神登天」，**不是**因为某一手选了什么，而是因为他**终局时同时站在"绝顶"和"心魔重"这两条线上**。
- 更麻烦的是 `near` 那一批里的随机（`:2726`）。同一局状态重跑，可能拿到 `near` 里另一个结局。**如果界面写成"因为你选了第某节那一手，所以得到此局"，那是在编一个引擎里不存在的因果。**
- 这违反 CLAUDE.md 自己定的铁律：**「提示必须与行为对得上」**。"说得不准比不说更糟"，归因尤其如此 —— 玩家会照着错的复盘去改下一世。

**替代提法（我建议主 AI 采纳）**，把总结的语气从"因为…所以…"换成"**你走到了哪里，于是最近的那个说法是…**"：

> 你这一世走到了这个位置。
> 几个结局都离你很近 —— 这个最近，于是它落在了你头上。
> 回头看一眼是哪个岔口把你送到这儿的。

**唯一有真因果的情况，要单独、明确地说出来**：剧本破局或 `trigger_end` 直接指定的结局（`engine.ts:2711-2712` 的 `forced`，来源 `pending_ending` / `ending_threads`）。这时候**可以也应该**说死："这一手定了你这一世的收场"——而且这句话**已经有了**，在 `preview.ts:followupOf()` 里（选项预告里那句「这一手会定你这一世的收场」，`preview.ts:133`）。

所以归因界面要**分两副面孔**：

| 结局来源 | 界面怎么说 | 数据判据 |
|---|---|---|
| **挣来的**（`forced`） | 明确归因："你在《某剧》里那一手，定了这一世的收场" | `pending_ending \|\| ending_threads` 非空 → `resolveEnding` 的 `forced` 分支 |
| **落进来的**（贴合度） | 诚实描述："你站在这个位置，最近的结局是它"，并列落选者 | `scored` / `near` |

**这个区分是本题最重要的专业判断。** 做成一副面孔，必然在多数局里撒谎。

2. `HistoryEntry.breakthrough_id` **真正写上**（`types.ts:564` 声明了未用）。在破局那一步的 history 记录里填 `breakthrough_id`。顺便：`submitScenarioEntry`（`engine.ts:2053-2088`）也该记一条 history，否则"你绕开过"这件事在复盘里不存在。

**交互路径**

```
一世终结 → EndingScreen（结局卷轴，仍是现在这副"看"的样子）
   → 点【回看这一世】→ 归因页（同一屏内滚动展开，不跳路由）
   → 归因页可滚动，四个层次从上到下
   → 底部仍是【再入轮回】/【回到卷首】
```

**为什么不做成"结局页直接铺满归因"**：结局卷轴的价值在**仪式感**——`EndingScreen.tsx:1-9` 的注释写得很清楚，"卷轴是已经写好的东西，用整卷展开而不是即时书写"。把归因塞进同一屏，仪式感会被表格冲掉。**先给情绪，再给复盘**，两侧各得其所。

**文本分两层，别混（这一条关系到硬门禁）**

- **诊断行**（"心魔 已深"、"道行 距绝顶一步"）：这是**界面读数**，不是叙事。可以含数值与属性名 —— 现有界面已经在这么做了（`StatusBar.tsx:267` 显示属性名、`ScenarioScreen.tsx` 的"还差"栏显示 `shortfall` 原文、通篇 `x-num` 显示阿拉伯数字）。`content-lint` 的 `no_numbers` 规则**只扫叙事池** `c.l2`（`tools/content-lint.ts:315-330`）。
- **结语/叙事行**：**严守文本禁区** —— 第二人称「你」、三行、每行 ≤60 字、无阿拉伯数字、无属性名/资源名/系统词。

  示例（合规范）：
  ```
  你走完了这一世。
  回头那几个岔口，你都还记得自己是怎么选的。
  再往前，路仍然认你。
  ```

**关于「属性名能不能出现在归因里」这一条，我要留个问号。** 文本禁区写着"不得出现…属性名"，但现有界面**已经在显示**属性名（`StatusBar.tsx:267` 的六维条、`GenesisScreen.tsx:105` 的"根骨 +5"）。所以我的读法是：**禁区管的是叙事文本，不管界面标签**；`no_numbers` 门禁的实现（只扫 `c.l2`）支持这个读法。若主 AI 的读法不同，请以 `engineer` 对门禁实现的口径为准 —— 我按"诊断行可含属性名"来设计，若口径相反，把诊断行改成"这副身子 / 那点灵性"这类代称即可，结构不变。

### 2.5 依据

**引用的资料**

1. Wikipedia, *After-action review* — https://en.wikipedia.org/wiki/After-action_review
   > "An after action review (AAR) is a technique for improving process and execution by **analyzing the intended outcome and actual outcome of an action and identifying practices to sustain, and practices to improve or initiate**…"

   归因页的目标形态就是 AAR：**意图 vs 实际**的对照，而不是成果清单。①「它认这几件事」= 意图；①「你走成了这样」= 实际；两者并排，差在哪一眼可见。

2. Slay the Spire Wiki, *Score*（经 MediaWiki API 取得，`slay-the-spire.fandom.com/api.php?action=parse&page=Score`）
   > "The table below is **additive scoring** (for each action performed)." — Floors Climbed / Enemies Slain / Exordium Elites Killed / Bosses Slain / Ascension / **Champion**（"Defeat an Elite without taking damage"）/ **Perfect** / **Overkill** …

   这是 roguelike 复盘的**主流范式：加法制计分 + 命名的成就徽章**。它答的是"我打得怎么样"，**不答"我为什么是这个结局"**。本作的结局系统比它多一层因果（`requires` 条件树）——**放着不用是浪费**，这也是本方案在范式上超出参照物的地方。

3. Don Norman, *Signifiers, not affordances* — https://jnd.org/signifiers-not-affordances/
   > "…**what is happening**, and what the alternative actions are."

   归因页的 ②「差一点的是哪个」正是一种 signifier：它把**没走的那些路**变成可见的线索。玩家在结局时最想问的正是"还能怎样"。

**本项目现状**

### 2.6 验收

1. **不撒谎（最重要）**：找一局**非 `forced`** 的结局，归因页**不得**出现"因为…所以…"的句式。判据：`pending_ending` 与 `ending_threads` 皆为空时，① 的文案模板走的是"最近的结局"分支。这条要写成测试。
2. **同源**：归因页「它认这几件事」列出的条件条数，**等于** `ending.requires` 展开后的原子条件数。判据：改一条 `endings.json` 的 `requires`，归因页跟着变；若不变，说明是手写的，挂。
3. **可回溯**：③ 列出的每一手，都能在 `state.history` 里按 `node_index` + `option_id` 查到，且 `delta` 里确实含该结局的关键变量。判据：写一个测试，对随机若干局断言 `③ ⊆ history`。
4. **落选者非空即可解释**：② 至少给出一个落选结局，且"只差的那一条"能由 `shortfall()` 产出非空字符串。判据：`unmetText(blocking, ctx, content) !== ''`。
5. **`forced` 可辨**：剧本破局导致的结局，① 的文案与贴合度结局**明显不同**，且指向具体剧本名。判据：快照测试两种分支的输出不同。
6. **文本合规**：归因页里**属于叙事**的段落（三行正文、结语）过 `no_numbers` 的同一套正则（`/[0-9０-９]/` + `SYS_WORDS`，`tools/content-lint.ts:316-329`）。诊断行豁免，但豁免必须显式写在代码注释里，不能默默放过。

### 2.7 代价

- **归因页会剧透。** ② 告诉你"若身边无人，本可以是《独上》" —— 等于把另一个结局的达成条件告诉了玩家。这在 roguelike 里通常是**正面的**（给下一世目标），但会削弱"偶然撞见"的惊喜。缓解：② 里**隐藏结局不列**（`ending.category === '特殊彩蛋'` 或 `tier === 'S'` 的过滤掉）。
- **给玩家"最优解"的暗示**，可能把开放结局玩成 checklist。缓解：② 措辞用"本可以是"而不是"应该走"；且只列 `near` 邻域内的（差 0.15 以内），远处的结局不提 —— 反正玩家也够不着。
- **结局页从 1 屏变 2 屏**，节奏会慢一拍。这是可接受的：结局页本来就是停下来的时候。但**归因必须是"点开"而不是"自动展开"**，把选择权留给玩家。
- `resolveEnding` 的返回值要加字段，`HistoryEntry` 要真写 `breakthrough_id` —— **这会碰 `engine.ts`，与并行的其他专家可能冲突。** 建议主 AI 把这两处改动排到没有其他人动 `engine.ts` 的时段。

### 3.1 现状（我实测的，不是推测）

**这两行数字把问题说清楚了：**

- **气运是唯一从不出现在门槛里的属性** —— 它是纯隐性乘数（暴击、抽样、采药）。这在设定上极漂亮（"气运不可见，只在背后推你"），但玩家**永远看不到它工作**，所以必然怀疑它没用。
- **机敏被推高的次数最多（92 次，是第二名的两倍半），却和魅力一起在引擎里零存在感。** 玩家会觉得自己一直在加一个没用的东西 —— 而这个感觉**是对的**（就引擎而言）。
- 门槛查得最多的是**悟性**（39 次），它有一条很硬的钩子（修行增速）；**机敏 29 次门槛却没有钩子** —— 说明内容作者以为机敏在管事，而引擎里它只在 `0.35 + v*0.005` 这个公式里摆动（从 40 到 58，成功率从 55% 到 64%，**九个百分点**）。

### 3.2 判断

**（a）问题不在呈现层，先说清楚。** 用户说"这四项属性的作用都需要讲明"。但把现状讲明之后会发现：**根骨/悟性/心性/气运各有硬钩子，讲得清；机敏与魅力没有钩子，讲不清 —— 或者说，讲清了反而暴露它没用。**

我作为界面设计师能做的：**把已有的作用讲准**。我做不了的：**给机敏与魅力编出作用来**。后者是 `systems-designer` 的规则缺口。所以我的建议是**分两步走**，不要合并：

1. **第一步（可以立刻做）**：把**已经有真实钩子**的那几维讲明（根骨/悟性/心性/气运 + 机敏魅力在剧本门槛中的角色）。
2. **第二步（等 `systems-designer`）**：给机敏与魅力补真实钩子，再把文案补上。

**如果先做界面、后补规则，界面就会开始撒谎** —— 这是这个项目反复吃亏的同一类问题（"结构齐备内容是空的，且不报错"）。

**（b）讲在哪，比讲什么更重要。** 属性不该在状态条上讲 —— 状态条是**读数**的地方（`StatusBar.tsx:1-13` 的信息层级注释写得很明白：那是"我是谁/我有什么"）。说明该在两个地方：

- **转世页**（`GenesisScreen`）：玩家**第一次遇到**属性，且**此刻正要据此做选择**。这是唯一有决策后果的时刻。
- **状态条点开**：玩家**想查**的时候。属性行做成可点 → 展开一张属性卡。

**（c）说明必须派生，不能手写。** 六维 × 每条一句 = 看起来只有六句，但**它们会腐化**：`engine.ts:464` 的 `root/100` 一改，手写的"根骨决定你恢复得快不快"就开始说谎。所以：

**在 `src/core` 里加一张 `ATTR_ROLE` 表（内容由 `systems-designer` 定），UI 只渲染它。**

```ts
// 建议形态 —— 由 systems-designer 填写，ux-designer 只消费
export const ATTR_ROLE: Record<AttrKey, {
  /** 一句话：它管什么（界面直接用，不加工） */
  role: string
  /** 作用方式：推力型（改算式）还是门槛型（只在条件里读）*/
  mode: 'force' | 'gate' | 'both'
  /** 它在哪几处被读 —— 供界面生成"影响"清单，改引擎时同步改 */
  hooks: string[]
}>
```

`hooks` 是关键：它把"这一维在哪些地方被读"变成**可枚举的数据**，界面上的"影响"清单从它渲染。将来 `engine.ts:464` 那条改了，改 `ATTR_ROLE` 一处即可。

**（d）每一维要给玩家两件事：一句作用 + 一个方向感。**
只有"根骨影响自愈"是不够的 —— 玩家要判断的是**"我该不该要它"**。所以每维还要一个**方向**：高了会怎样。这同样派生自 `hooks` 里的公式（`/100` 是斜率），或者由 `systems-designer` 在 `ATTR_ROLE` 里直接给一句。

### 3.4 依据

**引用的资料**

1. Don Norman, *Signifiers, not affordances* — https://jnd.org/signifiers-not-affordances/
   > "People search for clues, for any sign that might help them cope and understand… **Designers need to provide these clues. Forget affordances: what people need, and what design must provide, are signifiers.**"

   属性条现在是个**没有 signifier 的 affordance**：它可读（有数字），但不指示"这数字能做什么"。玩家得自己摸索六个月才知道根骨管自愈。

2. WCAG 2.1 SC 1.4.3 — https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html
   > "…at least **4.5:1**… Large-scale text… at least **3:1**"

   属性条上那两格小字（"高：修行更快"）是 `--fs-2xs` 级别的**小字**，必须过 4.5:1。见 §4.1 实测 —— `--t4` 只有 3.19，**不能用在这一行**。

3. Wikipedia, *Slay the Spire* — https://en.wikipedia.org/wiki/Slay_the_Spire
   > "…**did not require the player to have to memorize what each symbol meant**…"

   这句是本题的直接依据：靠图标/符号让玩家自己记意思是**被证否**的做法。属性条现在正是"六个符号 + 六个数字，自己去记"。Mega Crit 的解法是**把含义写出来**。

### 3.5 验收

1. **终值可见**：转世页调 `divideInitAttrs()`（`genesis.ts:51-73`）的输入，屏幕上就能看到六个**终值**，不需要开局。判据：改一个天赋的 `add_attr`，转世页终值跟着变。
2. **说明同源**：属性卡里的每一句"它管哪几处"，都能在 `ATTR_ROLE[key].hooks` 里找到对应项；**改 `engine.ts` 的钩子必须同时改 `ATTR_ROLE`**。判据：加一条测试，断言 `ATTR_ROLE` 里出现的钩子位置字符串，与实际 grep 到的 `attrs.<key>` 位置**集合相等**。这条测试本身就是防腐化的闸门（对应 CLAUDE.md「加功能必须同时加闸门」）。
3. **不撒谎**：属性卡里对机敏/魅力的描述，**不得出现引擎里不存在的效果**。判据：`ATTR_ROLE.insight.hooks` 若只有剧本手段一处，界面上就只列一处。**列了两处而引擎只有一处，验收算挂。**
4. **气运的"看不见"要被解释**：气运卡上必须有那句"它不在任何门槛上露面，只在背后推你"（或等价表述）。判据：`ATTR_ROLE.luck.mode === 'force'`，界面据此渲染该句 —— 这是从数据派生，不是特例硬编码。
5. **对比度**：属性卡正文 ≥ 4.5:1，标题 ≥ 3:1。判据：见 §4.1 的实测表，只用达标 token。

### 3.6 代价

- **讲明属性作用会降低探索感。** 摸索"根骨到底干嘛"本身可以是一种乐趣。但本作的属性**已经参与结算**（不是纯 fluff），玩家不知道就等于在盲选 —— 而 CLAUDE.md 明说"**界面上任何'玩家不知道自己在选什么'的地方，都是在削自由度**"。所以这条代价我判断为**值得付**。
- **六维详解会变成一块"攻略"**，玩家可能照着最优解配点，压掉出身/天赋的多样性。缓解：说明只给**方向**（"伤好得快"），不给**斜率**（"每点多恢复百分之几"）。前者够做决策，后者只会催生最优解。
- **`ATTR_ROLE` 是新的一张表，多一个要维护的地方**。这是真成本。但比"六句手写文案 + 六处引擎代码各改各的"便宜 —— 尤其考虑到这个项目**已经因为"手写文案与真相源脱钩"吃过一次亏**（`gain_hint`/`path_hint` 1629 条全空，见 `preview.ts:1-31`）。
- 转世页加终值 + 六维详解，会让**开局流程变长**。缓解：终值直接并进现有的六维栏，不新增区块；详解是**点开的**，不挡开局。

### 4.1 暗色界面的对比度实测（用户提过"界面偏暗"）

我按 WCAG 公式算了 `theme.css` 里的全部文字 token（`--t1`…`--t5`，`theme.css:61-65`）对四层底色：

| `BagPanel.module.css:91` `.kindTag`（物类小字：兵器/丹药/符令） | **9px** | 是 | ❌ 3.19 |

**而承重的信息其实都是达标的** —— 这一条很重要，别把好的一起改了：

- 功能标签 `.tag`（破局条件唯一认的那枚金色小签）= `--gold-bright` = **9.80** ✅（`BagPanel.module.css:142-150`）
- 物事名 `.name` = `--paper` = **13.02** ✅（`:117-125`）
- 物事描述 `.desc` = `--t3` = **5.91** ✅（`:176-183`）
- 成色 `.wear` = `--t3`/`--warn`/`--cinnabar-txt` ✅（`:195-211`）

**所以"界面偏暗"的可测量部分是：主信息达标，次级标签集体不达标。** 修法是把那 21 处的 `--t4` 换成 `--t3`（5.91 ✅，仍是明显的层级差），**不需要也不应该动全局亮度** —— 暗底暖白是本项目的艺术方向，整体调亮会伤风格。

`--t5`（1.58–1.66）目前只做纯装饰，**保持这样**，别让它沾文字。

前景色方面（对 `ink-2`）：`--gold` 6.76 ✅、`--gold-bright` 9.80 ✅、`--jade-txt` 7.69 ✅、`--cinnabar-txt` 6.04 ✅、`--warn` 5.98 ✅、`--paper-mute` 7.98 ✅。
**但 `--jade`（对 `ink-2` = 3.36）与 `--cinnabar`（3.03）不达标** —— 项目已经为此准备了 `--jade-txt` / `--cinnabar-txt` 两个文字变体（`theme.css:47-48`），所以**规则是"文字用 `-txt` 变体，纯色块用本体"**。

不过 `BAND_STYLE`（`text.ts:189-194`）破了这条规则：`success` 用 `var(--jade)`、`crit_fail` 用 `var(--cinnabar)`。而这两处**是判决横幅上的文字**（`EventScreen.tsx:132-139`），`.x-band` 的字号是 `--fs-sm` = **0.86 × 16 ≈ 13.8px**（`theme.css:928-939`）—— 既不够 18pt 也不够 14pt 粗体，**按 WCAG 属于"正常字号"，须 ≥4.5:1，实测只有 3.36 / 3.03，不达标**。建议改用 `-txt` 变体（`--jade-txt` = 7.69、`--cinnabar-txt` = 6.04）。

判决横幅是"这一手成了没有"的第一眼反馈，**它读不清是比标签读不清更严重的事**。

所以"界面偏暗"的**可测量部分**不是整体亮度不足，而是**少数几处用了低对比 token 写小字**。整体亮度不宜乱调 —— 暗底配暖白是这个项目的美术方向，动了会伤风格。

### 4.2 关于「不显示精确成功率」——我不同意改，但要区分两件事

`EventScreen.tsx:5-6` 写着"我们刻意不显示精确成功率：那是「算计」，不是「修行」"。这与§1.4 引的《杀戮尖塔》教训方向相反。

**我判断这个取舍在本作是成立的**，理由：本作的核心卖点是**信息不对称下的智性破局**（CLAUDE.md 设计方向第 3 条），而《杀戮尖塔》是纯数值构筑。**把"未知"当玩法，和"让玩家找不到东西"是两回事。**

但我要立一条界：

> **「未知」是玩法，是设计出来的、有回报的（参透隐规则就是这个回报）。「找不到」是缺陷，是没设计。**
> 行囊看不见属于后者。判定成功率看不见属于前者。

这条界建议写进 CLAUDE.md 或设计文档，免得下次把两者混为一谈 —— 混了就会有人拿"界面上不给数字"当借口，把真缺陷也一起辩护掉。

### 4.3 `dl_ink`：一个会把内部 id 显示给玩家的标签

`affordanceLabel()`（`text.ts:315-317`）只做 `replace(/[_-]/g, ' ')`。而全仓 33 个功能标签里，**`dl_ink` 是唯一一个非中文 id**（`items/affixes.json:567`，并被 7 个剧本的破局条件引用：`scn_cross_new_law.json:79`、`scn_mystery_three_seats.json:57/163`、`scn_physique_name_casket.json:80`、`scn_physique_early_tally.json:178`、`scn_rebel_question_hall.json:184`、`scn_mortal_name_stele.json:126`）。

**它会被渲染成「dl ink」出现在行囊格子的金色小签上。** 这直接违反"文本禁区：不得出现…系统词"，而且是玩家一眼能看出来的那种。修法二选一：内容侧改名，或 `affordanceLabel` 加一层 id→中文的映射。

### 4.4 一个我建议加的门禁

本方案里的 §1.5 第 3 条、§2.6 第 2 条、§3.5 第 2 条都是同一个形状的验收：**派生文本必须与真相源同源**。这个项目已经吃过 `gain_hint`/`path_hint` 全空的亏（`preview.ts:1-31` 的注释）与"预告开始撒谎"的亏。

建议在 `tools/content-lint.ts` 加一条 **`derived_hint_parity`**：对凡是"界面文案由真相源派生"的地方（选项预告、入场简报、归因条件、"还差什么"、属性作用），加一个**改真相源 → 断言文案随之改变**的测试。文书写"我们做了派生"是不够的，**要有一条测试在派生断掉时变红**。

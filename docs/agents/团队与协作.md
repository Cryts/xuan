# 《玄》专家组 · 分工与协作规则

> 建立于 2026-09-20。目的：**改动先过对应专家，而不是由主 AI 一人拍板。**

## 一、为什么是这几个角色

按真实游戏项目组的分工设置（参考 `en.wikipedia.org/wiki/Video_game_development`
的 Roles 一节与 `Game_design`）。商业项目组里通常有：制作人 / 设计（系统、关卡、叙事）/
美术 / 程序 / 音频 / 测试 / 文案，独立小团队则把音频、测试、制作合并。

《玄》是单人文本游戏，没有音频与关卡（关卡被"剧本"吸收），所以保留并强化这七个：

| 专家 | 对应项目组角色 | 一句话职责 | 决策权 |
|---|---|---|---|
| `systems-designer` | systems + economy + balance | 数值、经济、曲线、支配性 | **数值问题的第一决策人** |
| `narrative-designer` | narrative designer | 事件结构、衔接、人物关系、结局归因 | **故事结构的第一决策人** |
| `gameplay-designer` | gameplay + level + progression | 玩家能做什么、好不好玩、成就与奖励 | **玩法问题的第一决策人** |
| `worldbuilder` | lore master | 六体系自洽、寿命尺度、天命榜 | **设定自洽的第一决策人** |
| `ux-designer` | UI + UX + 美术指导 | 决策时刻的信息完备性、视觉 | **界面问题的第一决策人** |
| `writer` | staff writer | 怎么写（不是写什么） | **文风的第一决策人** |
| `engineer` | tech lead + tools | 架构、约束、门禁、测量可信度 | **技术问题的第一决策人** |

### 刻意不设的角色

- **音频**：文字游戏没有音频层（`src/ui/sfx.ts` 只有点击音效，不值得设岗）
- **制作人/项目经理**：这个角色由**主 AI + 用户的 todo 列表**承担
- **QA**：`tools/playtest.ts` 已经是自动化的试玩 agent，比人更不知疲倦；
  但它**只测覆盖率与卡点，不测好不好玩** —— 好不好玩归 `gameplay-designer`
- **IP 合规**：已经是硬门禁（`tools/content-lint.ts` 的 `ip_clean`），不需要专家，
  需要的是**不可绕过**

## 二、协作规则（主 AI 必须遵守）

1. **先问，再做。** 任何改动，先判断它归谁管，把问题丢给对应专家，**拿到意见再动手**。
   主 AI 不再是所有事情的决定者，而是**协调者 + 执行者**。
2. **专家有权说不。** 如果主 AI 的方案在本专业上站不住，专家要直接指出并给替代方案。
   主 AI 不能因为"我已经想好了"就跳过这一步。
3. **意见冲突时**：由涉及的两个专家各自给依据，主 AI 汇总后**报给用户裁决**，
   不要自己挑一个顺手的。
4. **专家的结论必须有依据**：实测量出来的数、或者引用的资料。
   "我觉得应该……"不算依据。
5. **每个专家都要做研究。** 被问到不确定的问题时先去查资料（联网走代理，见下），
   **不要凭训练印象发言** —— 训练印象恰恰是不同专家趋于雷同的原因。
6. **验收仍归主 AI**：专家给方案，主 AI 负责实现、跑门禁、贴证据。

| 问题 | 归属 |
|---|---|
| 日常收益应接近但有侧重与方差；坊市消耗灵石不产出物品；灵石应随境界增长；事件应是意外之财 | `systems-designer`（经济）+ `gameplay-designer` |

| 结局应与选项关联，要有归因总结 | `narrative-designer` + `ux-designer` |
| 剧本里每次选项都算时间，太容易暴毙 | `systems-designer`（主）· `engineer` |
| 高修为应更难达成；每局时间应增加；修为应趋正态分布 | `systems-designer` |

# 文字修仙小游戏开源项目调研与设计建议

## 摘要：以规则系统保证稳定性，以 AI 提升表达密度

调研结论可以归纳为四点：

1. **可发布产品的核心不应是“LLM 能否生成剧情”，而应是规则、随机与存档能否形成可验证的单局循环。** 万界道友官网已明确：AI 用于文本、命名、事件描述和奇遇表达，核心数值、资源、奖励及状态变化仍须经过游戏规则校验，不会只由 AI 决定 [1]。灵界官网也将业务随机定义为服务端安全随机 [4]。这两项设计共同指向一个原则：**AI 负责表达层，规则引擎负责状态层。**

2. **“轻量单局—构筑积累—轮回重开”已经得到产品验证。** 文字修仙模拟器官网将单局时长描述为“通常几分钟”，并通过随机转世、天赋抽取、20 点先天属性、事件流和重开构成核心循环 [3]。这种结构特别适合微信小程序和碎片化网页场景，但短局本身不足以形成长期留存；长线动力仍需来自跨局解锁、构筑差异与元进度。

3. **网页端应优先采用规则数据驱动，再选择性加入 AI 润色。** 推荐架构为：配置静态化并部署至 CDN；将用户存档、交易和排行榜放入服务端受控数据库；由规则引擎保存状态真相（source of truth）；仅在剧情、命名、奇遇文本等低风险环节调用 LLM。AIDungeon 证明了自由生成的表达潜力，也暴露出训练与运行成本较高的问题 [7]，不宜直接复制到面向大众的小程序产品。

4. **AIGC 上线受平台合规与主体资质约束。** 微信官方指引要求提供深度合成服务的小程序补充相应类目，并按自研或第三方技术路径提供算法备案、合作协议等材料；输入和输出内容还须接入安全检测机制，并建议叠加人工审核 [10]。因此，更稳妥的产品路线是先以模板化内容和非公开测试验证玩法，再逐步开放 AI 生成，而不是先全量上线无约束的玩家输入。

综合判断：**MVP（最小可行产品）宜采用“短局轮回 + 数据驱动事件 + 服务端规则校验”，AI 只承担可选文本层；当内容量、留存与合规条件成熟后，再扩展到长线世界与开放表达。**

## 1. 调研边界决定结论可信度：产品事实、架构借鉴与合规提示必须分开

**本报告可以确认产品机制和平台要求，但不能据此推定源码实现或经营数据。** 调研覆盖用户指定的三款产品，并补充“我的文字修仙全靠刷”、AIDungeon、Evennia、Ranvier MUD 及微信云开发。前者用于研究玩法，后三者分别用于借鉴内容配置、多人文本状态和轻后端架构；它们不是对指定产品的源码审计。

信息优先级依次为官网、原始代码仓库或官方文档，其次才是社区和镜像。技术栈、许可及更新状态如果只能由 README、代码文件或第三方索引间接推断，均标注为“未能完全核实”或“社区资料”。Star 数、商业收入、具体并发能力、留存数据和精确 DAU 不在本次可核验证据范围内，不因第三方文章存在相关描述而视为已确认。

**“开源”必须落实到具体许可。** 万界道友仓库 README 明确采用 GPL-3.0 [2]；AIDungeon 仓库同样包含 LICENSE 文件，第三方索引显示为 MIT [7][14]。其它项目的 LICENSE 存在性可以核对，但协议正文仍须在上线前逐一复核。

**AI 项目还需要区分“使用模型”与“分发模型”。** 即使上游权重可免费调用，也并不意味着下游可以无条件商用；即使项目许可证允许修改，下游产品仍可能受到不同主体、不同算法备案状态和平台类目的约束。因此，开源许可、模型服务条款、算法备案及小程序审核材料应分别管理，不能用其中一项替代另一项。

**核心设计取舍已经明确：AI 应靠近表达层，规则应独占状态层。** 文字修仙的修为、突破、寿命、资源、伤害和掉落直接决定玩家资产与胜负，必须由确定性的服务端规则计算。LLM 则适合承担事件标题、环境描述、NPC 语气和结局旁白，并通过模板、JSON Schema 和事后校验约束输出。这样既能获得新鲜感，也能避免模型直接操纵数值后造成不可回放、不可审计和不可补偿的问题。

## 3. 四维度归纳：自由度必须建立在稳定、轻量与长线系统之上

**四个维度的优先级并非并列：稳定性是发布底线，轻松性是获客入口，游戏性决定留存，自由度则应在前三者成熟后扩展。** 如果顺序倒置，直接追求开放剧情或复杂社交，往往会同时放大成本、不一致和合规风险。

### 3.1 稳定性：所有玩家可见状态必须只有一个权威来源

**稳定性并不等于“内容不变化”，而是同一操作在同等条件下必须产生可审计、可回放的结果。** 灵界官网将随机定义为服务端安全随机 [4]；万界道友则将 AI 限定在文本表达层，核心数值、资源、奖励和状态变化仍由规则校验 [1]。两者共同否定了两种高风险做法：让模型直接决定掉落数量，或让客户端掷骰后再向服务端申报结果。

推荐的服务端权威流程如下：

```text
玩家动作
  → API Gateway / 云函数
  → 鉴权 + 动作校验
  → 服务端 RNG（种子、用户、回合、 nonce）
  → 规则引擎计算 delta
  → 写入 event-sourced 日志与玩家状态
  → 返回受控表现数据
```

LLM 只能在日志落盘后生成旁白，不能通过生成“获得 9999 灵石”一类文本直接修改余额。若模型输出影响数值，系统也必须先将其解析为结构化提案，再由规则层重新计算、封顶和持久化。

**对结算类内容采用 JSON，而非自然语言。** 可将事件定义为：

```json
{
  "id": "qixue.mountain",
  "weight": 100,
  "requires": { "realm": ">=2", "hp_ratio": "<=0.8" },
  "effects": [
    { "type": "add_resource", "key": "lingstone", "min": 10, "max": 30 }
  ],
  "narrative_pool": ["lingverse.qixue.mountain.a", "lingverse.qixue.mountain.b"]
}
```

模型只需填充 `narrative_pool` 中经过人工审核的变量槽位，或根据主题生成候选文本。这样，即使生成失败，也不会影响数值结算。

**存档必须能重放和修复。** 最小日志结构可同时记录状态快照和动作事件：

```json
{
  "snapshot": {
    "version": 12,
    "at": "2026-09-20T10:00:00Z",
    "state": {}
  },
  "events": [
    {
      "id": "evt_01",
      "type": "breakthrough.attempt",
      "input": {},
      "result": {},
      "rule_version": "2026-09"
    }
  ]
}
```

发生补偿时，系统可以重放事件、比对哈希并定位分歧。快照加事件流会增加工程成本，但远比直接覆盖玩家状态更容易排查 AI 或版本异常。

### 3.2 轻松性：控制首次决策，但不消除有意义的构筑

**“几分钟一局”的价值在于低门槛，不在于内容贫乏。** 文字修仙模拟器官网明确“通常几分钟一局”，并将天赋、属性和随机事件组织为一次完整人生 [3]。首局应让玩家在 30 秒内进入第一次命运变化，尽量减少新手教程、复杂词表和重复确认。

推荐的首局节奏为：

1. 随机出身或建议天赋；
2. 一键再抽，避免逐格配置；
3. 第一次事件在两至三步内发生；
4. 一分钟内看到属性或资源变化；
5. 五分钟内到达第一个小型结局或转世节点。

这不等于将所有选择削平。关键属性仍应支持构筑，但应通过“出身 + 三项天赋 + 一个核心缺陷”等少量、高差异的旋钮呈现。玩家需要的是能快速理解因果关系，而不是面对大量无明显差异的点数。

**离线收益应补偿时间，而不制造被迫等待。** 放置部分可采用“离线最多结算 8 小时，上线一键领取”或“每 10 分钟自动突破一格”等保守规则。真正的策略应来自修炼路线、装备词条和事件选择，而不是要求玩家定时点击。

对于小程序，首屏可使用本地缓存恢复进度；云端存档则在登录后静默合并。合并策略必须以服务端版本号、设备 ID 和操作日志解决冲突，不能简单采用最后写入者获胜（LWW），否则跨端切换可能直接覆盖有效进度。

### 3.3 游戏性：短局轮回必须沉淀为跨局长线成长

**重开只有在改变下一局起点时才构成机制，否则只是清空失败。** 文字修仙模拟器的天赋、属性、事件和再入轮回适合快速尝鲜 [3]；灵界则将冥想、探索、突破、洞府、坊市、宗门和灵宠连接为多日长线循环 [4]。

自研产品可将两者结合：

- 单局持续 5 至 15 分钟；
- 死亡或飞升后进入转世；
- 元货币、图鉴、命格和已解锁事件保留；
- 每局仍保留足够强的随机性，避免完全脚本化。

**构筑深度应通过可组合的少量系统产生，而不是无边界地堆叠系统。** 例如，“灵根—功法—法宝—丹药”四条线即可形成多种流派：

- 火灵根强化爆发；
- 木灵根强化续航；
- 剑道提升单体伤害；
- 丹道通过资源转换提升容错。

每种流派都应具有明确的上限、克星和装备偏好。如果所有系统只汇成单一战力数值，玩家会失去选择动机；如果系统过多而资源转换不透明，又会提高理解成本。合适的目标是：玩家能清楚解释“为什么这样更强”，而不是只看到战力标签变大。

**经济系统必须延迟开放。** 灵界的坊市、拍卖和宗门表明，玩家交易与社交可以成为长线动力 [4]，但公开经济会同时放大脚本、工作室和通货膨胀风险。MVP 可先采用受控 NPC 商店、固定兑换和每日价格带，再引入玩家交易。所有交易价格、手续费和税率都应进入可热更新的平衡表，而不是硬编码在客户端。

### 3.4 自由度：从高质量分支起步，再逐步扩展到开放输入

**自由度并非只有“自由输入”一种形态。** 文字修仙模拟器通过天赋和属性影响事件走向 [3]，自由度适中；AIDungeon 支持自然语言动作，自由度最高 [7]；万界道友则试图以 AI 表达增强传统修仙系统 [1][2]。对团队规模有限的商业产品而言，更合理的路线是：

1. 数据驱动分支；
2. 槽位化文本生成；
3. 开放意图解析；
4. 受信任的沙盒式世界编辑。

每一步都应在内容安全、测试覆盖和运营成本达到条件后再开放。

**叙事表达可采用分层生成，避免被单一模型质量绑架。**

| 层级 | 典型内容 | 可接受延迟 | 主要控制方式 |
|---|---|---:|---|
| L0 | 规则文本、教程、失败提示 | <50 ms | 静态模板 |
| L1 | 基于玩家状态组合的剧情、命名 | <200 ms | 模板 + 变量 |
| L2 | 事件引言、NPC 语气 | <1.5 s | 审核模板或缓存 LLM 结果 |
| L3 | 高度分支的奇遇、玩家自定义命名 | 可接受流式加载 | 受约束 LLM |

如果 L0/L1 已经能让玩家继续推进，LLM 超时就不必阻断玩法。所有 AI 生成结果都应经过敏感词、未成年保护、低俗色情和有害指令检测，并配置重试及降级模板。

## 4. 推荐技术架构：H5 优先复用，服务端采用可演化的双速模型

**最终目标不是一次建成 MUD，而是在 H5 与小程序复用一套规则核心。** 建议采用“一个设计系统、两个视图层、一个规则后端”，避免在项目早期分别为网页和小程序维护两套数值逻辑。

### 4.1 前端：H5 作为产品底座，跨端方案根据团队能力选择

**H5 应成为设计与内容实验的底座，小程序作为受约束的分发端。** 网页端可以更快迭代文本流、表格、剧情分支和运营页面；小程序则更适合分享、通知和留存。两者差异不在于是否使用同一套 UI 库，而在于能否共享状态机和内容数据。

如果团队以 React/TypeScript 为主，可采用 React + Vite 构建 H5，再使用 Taro 输出微信小程序。如果团队更熟悉 Vue，可使用 Vue 3 复用“我的文字修仙全靠刷”所代表的 Vue/Pinia 工程经验 [6]，再通过 uni-app 跨端。跨端框架能减少重复代码，但也会增加运行时、调试链路和小程序体积；如果只有小程序一个目标平台，且团队熟悉原生开发，则不必仅因技术潮流引入额外抽象。

**统一游戏层，而不是统一所有 UI 组件。** 建议拆分以下模块：

- `game-core`：状态机、事件解析器、战斗公式、随机接口、存档序列化；
- `content`：境界、天赋、事件、物品、区域、任务和叙事模板；
- `app-h5` / `app-miniprogram`：页面、路由、分享和支付适配。

`game-core` 不依赖 DOM、小程序 API 或 LLM SDK。这样既能先在浏览器中快速迭代，也能后续移植到小程序、小游戏或原生 App。

**内容渲染应支持纯文本、卡片和轻交互三种模式。** 自动剧情可表现为逐段滚动文本；重要事件使用“插图 + 三项选择 + 概率提示”的卡片；战斗采用压缩后的伤害摘要。文字游戏的优势是低带宽，不应强制加入重 Canvas 或 3D 特效；每张场景图都应可降级为纯 CSS 水墨背景。

### 4.2 后端：先从小程序原生云开发起步，再向容器化迁移

**MVP 使用微信云开发，长期复杂世界采用 CloudBase 云托管或独立服务。** 微信官方文档说明，云开发提供云函数、JSON 数据库、存储和静态网站，并支持免鉴权调用 [11]；CloudBase 还提供 Postgres、文档数据库、云函数、云托管及静态托管等完整组合 [12]。

首期建议：

| 能力 | 首期实现 | 后续演化 |
|---|---|---|
| 登录 | 云开发鉴权 | 邮箱、手机号、第三方登录 |
| 存档 | JSON 数据库 | Postgres / MySQL |
| 玩法计算 | 云函数 | 独立规则服务 |
| 配置 | 数据库 + CDN | 版本化配置中心 |
| 静态资源 | 静态托管 | CDN + 灰度发布 |
| AI 调用 | 单一云函数 | Agent 网关、缓存与降级 |

当同时在线、复杂副本或长连接需求明显时，可将规则服务迁移到 Go/Node 容器，但接口契约应保持稳定。

**读写边界应遵循“客户端只读状态，服务端独占写入”。** 云数据库安全规则只允许客户端读取公开配置和自己的存档；修炼结算、掉落、突破、交易、签到、礼包和排行榜全部通过云函数执行。即使是单机向玩法，也应同步一份“可信存档”，以便后续支持跨端、反作弊和客服修复。

微信云开发提供 HTTP API，可用于网页端复用同一后端 [13]。但网页端鉴权、域名和安全策略仍须单独设计，不能将小程序内部调用逻辑原样复制到浏览器。

**规则服务应独立部署为无状态计算单元。** 请求只需包含动作与版本：

```json
{
  "action": "explore.wild",
  "rng": {
    "seed": "srv_generated",
    "round": 12873
  },
  "rule_version": "2026-09",
  "content_version": "1.12.3"
}
```

响应必须包含事件 ID、数值 delta、随机证明摘要和下一步可选项。模型调用不得混入同一事务：规则事务提交后，异步任务再生成文本，从而将“玩家资产变更”与“文本体验”彻底隔离。

### 4.3 数据与配置：公开内容 CDN 化，私有状态服务端化

**配置静态化与动态热更新并不冲突，关键是区分公开内容和私有状态。** 可将以下数据放入版本化 JSON：

- 境界曲线；
- 天赋；
- 事件权重；
- 掉落表；
- 商店；
- 任务；
- 文本模板。

资源发布时生成 `content-{hash}.json`，并通过 CDN 缓存。客户端启动后先获取 `manifest.json`，再按需下载差异包。公开内容适合 CDN，是因为所有在线玩家共享同一版本；玩家存档、交易和排行榜属于私有状态，必须由服务端持久化。

**配置应拆分为内容、数值和本地化三层。**

| 层级 | 主要内容 | 变更方式 |
|---|---|---|
| content | id、触发条件、权重、奖励、下一节点 | 可热更 |
| balance | 曲线、概率、价格、冷却 | 受控灰度 |
| i18n / narrative | 中文文本、命名、旁白 | 模板、审核或 AI 填充 |

同一事件可绑定多个叙事模板，并在不同区域或版本中切换。这样既能支持 A/B 测试，也便于后续接入 AI 润色。

**数值版本必须参与所有结算。** 配置表应包含：

```json
{
  "id": "event.001",
  "version": "1.12.3",
  "rule_ref": "engine@2026-09",
  "tags": ["open_mountain", "early_realm"]
}
```

如果线上发现错误，可以通过事件日志和版本号重放、补偿或回滚，而不是笼统地“修复数据库”。

## 5. LLM 接入：低成本高可用来自受约束架构，而不是更贵的模型

**LLM 的正确定位是受约束的内容函数，而不是游戏规则或在线 GM。** 万界道友的设计可以作为边界参照：AI 承担文本、命名、事件描述和奇遇表达，核心数值经过规则校验 [1]。自研产品应进一步落实为“结构化动作 + 受约束生成 + 规则校验”。

```text
玩家输入（可选自然语言）
  → 意图分类器
  → 白名单动作映射
  → 规则引擎计算
  → 结构化事件结果
  → LLM 填充 flavour（可选）
  → 内容安全过滤
  → 客户端渲染
```

如果输入无法映射到白名单，系统应回退为“你说的话没能化为法诀”，而不是让模型自由决定世界状态。

**生成质量应通过 schema 约束，而不是依赖提示词中的道德劝说。** 云函数侧可采用：

- 小模型负责意图分类和实体抽取；
- 主模型负责标题或旁白；
- 结构化输出强制为 `{title, lines[3], mood, tags[]}`；
- 长度限制为 120 字以内；
- 禁止使用资源、数值、身份和命令类名词；
- 输出后使用正则、敏感词和 JSON Schema 校验。

模型还可能产生语言混杂、重复、OOC（脱离角色）、文化或版权风险，以及数值越界。因此，最大输入长度、上下文截断、输出长度、重复惩罚和超时都应受到工程限制。

**模板库比全量生成更能降低成本和风险。** 事件正文可按“触发条件 + 角色属性 + 结局类型”组织：

```json
{
  "pool": "qixue.mountain",
  "condition": {
    "realm": "early",
    "has_item": "fire_charm"
  },
  "template": "在{location}的雾气中，{npc_role}递来一枚{item}，暗示你{choice_hint}。",
  "variables": {
    "npc_role": ["采药人", "散修"],
    "item": ["残破玉简", "火属性灵石"]
  }
}
```

L1 可通过变量组合覆盖 80% 以上的内容；只有高价值玩家、节日活动或稀缺奇遇才调用 LLM。这样既可控制费用，也能让人工审核集中在少量模板上。

**缓存与降级决定生产可用性。** 建议采用以下顺序：

1. 内容 hash + 玩家状态桶；
2. 检索预生成文本；
3. 调用模型；
4. 异步落盘；
5. 审核后发布。

同一事件、相近境界和相同标签可以复用候选文本，但应加入轻微变量扰动，避免重复。降级优先级如下：

- 一级：预设高质量文本；
- 二级：规则生成的极简文本；
- 三级：纯状态变化，不展示剧情。

流式输出只用于非结算文本，不能在流式中承诺资源，也不能在玩家已看到“获得奖励”后再撤回。

**可观测性必须覆盖质量和成本。** 每次调用应记录：

- prompt 与 completion token；
- 模型版本；
- 延迟；
- 缓存命中；
- 敏感词命中；
- 重试次数；
- 事件 ID；
- 最终展示率。

还需按事件池和玩家分群统计文本展示率、负面反馈、重开率和付费转化。没有这些指标，就无法判断 LLM 是否真正改善体验，还是只增加了延迟和支出。

## 6. 内容合规：AIGC 不是普通功能开关，而是独立的审核与运营系统

**微信平台要求将深度合成视为正式服务类目，而不是一个隐藏开关。** 微信官方指引指出，存在深度合成服务的小程序应补充“深度合成服务”类目。自研技术需提供小程序主体的生成合成类算法备案或审批中截图；使用第三方技术，还需提供技术主体的算法备案及双方合作协议，且协议应包含算法名称、应用产品或备案编号等信息 [10]。

目前证据只能支持上述平台要求，不能证明任意模型服务、备案状态或合作协议必然通过审核。上线前仍须根据发布当时的官方规则、所选模型服务商和主体情况进行复核。

**UGC 与 AIGC 应采用更严格的二分法。**

| 内容形态 | 最低控制策略 |
|---|---|
| 玩家完全自由输入 | 登录或实名；频率限制；输入审核；输出审核；人工巡检；举报；撤回；日志 |
| 玩家从选项列表行动 | 固定选项审核；模型仅填充非结算文本；输入输出审核 |
| 纯预生成内容 | 上线前审核；变更记录；版本回滚 |

如果只提供固定选项，模型只填充 flavour，风险显著低于自由对话。但即使采用固定选项，也不能省略输出审核。

**输入与输出都应设置多层拦截。** 微信指引要求小程序用户输入接入内容安全检测机制，并建议叠加更多过滤机制和人工审核；输出内容同样须经过过滤 [10]。建议采用：

- 第一层：客户端长度限制、频率限制和敏感词拦截；
- 第二层：服务端模型厂商及云平台审核；
- 第三层：业务规则拦截，例如禁止生成联系方式、外链和未成年人不当内容；
- 第四层：抽样人工审核及举报闭环。

文本审核可能误杀，因此应保留“修改后重试”和人工申诉入口，但不能让玩家绕过核心规则。

**AI 生成标识、隐私和未成年人保护必须进入产品流程。** 微信社区案例要求 AI 生成页面显著标注“AI 生成”或同等含义 [15]。产品应在生成文本附近固定展示标识，并记录生成时间、模型和版本；不得展示完整 prompt、内部规则或其他玩家隐私。聊天记录、昵称和存档用于模型上下文时，应先脱敏并取得必要授权。

如果涉及实名、防沉迷或未成年人，应遵循适用平台规则。灵界官网提及 TapTap 实名与防沉迷，但该信息只能说明灵界的做法，不能替代自研产品的法律意见 [4]。

**运营机制也应限制生成扩散。**

- 每个账号每日 AI 生成次数受限；
- 高风险场景仅向成年或完成实名玩家开放；
- 建立模型供应商、词库和模板的灰度开关；
- 预设紧急关闭能力；
- 建立投诉、下架和复盘 SOP。

发生严重输出时，应能够按 `tenant + model + template + version` 立即停用，而不是等待全量发版。

## 7. 12 周 MVP 路线：先证明规则循环，再增加 AI 与社交

**MVP 的目标不是复刻完整修真 MMO，而是验证短局轮回能否形成留存。** 如果核心事件、构筑和转世尚未成立，提前加入 AI、宗门、交易或开放世界只会放大维护成本。

| 阶段 | 周期 | 交付物 | 验收指标（研究建议） |
|---|---:|---|---|
| 0. 设计契约 | 第 1 周 | 境界、属性、天赋、资源、事件和战斗的状态图；禁止 AI 修改的字段清单 | 所有结算均可离线重放 |
| 1. H5 纸带 | 第 2–4 周 | React/Vue 纸带、事件卡、规则引擎、本地存档 | 5 分钟内完成一局，死亡或飞升后可重开 |
| 2. 服务端真相 | 第 5–6 周 | 云函数、JSON 数据库、受控 RNG、配置 CDN | 篡改本地存档不会获得有效资源 |
| 3. 内容与构筑 | 第 7–8 周 | 100 个以上事件、天赋、装备词条、元进度 | 至少 5 种可感知构筑；内容可热更 |
| 4. AI 文本试点 | 第 9–10 周 | 模板库、LLM 旁白、缓存和降级 | AI 失败不影响结算；P95 文本延迟可控 |
| 5. 小程序与合规 | 第 11–12 周 | Taro/uni-app 或原生适配、登录分享、审核闭环 | 首屏可玩；核心流程覆盖输入输出审核 |

**MVP 事件池应覆盖三类循环：短、中、长。**

- 短循环为 30 秒至 5 分钟，包含一次修炼、事件和结算；
- 中循环为 5 至 15 分钟，包含突破、装备和一次死亡或飞升；
- 长循环为多局转世、图鉴、命格和赛季。

如果短循环无法成立，开放世界和社交没有意义；如果中循环缺乏构筑，AI 剧情再丰富也容易变成一次性消费品；如果长循环没有元解锁，重开会逐渐失去动机。

**灰度顺序应与风险一致：先固定内容，再开放生成。**

1. 先上线固定选项和非生成内容；
2. 再开放 AI 命名与结局 flavour；
3. 再试点玩家自由输入；
4. 最后考虑 UGC 分享和公共世界观编辑。

每次开放新能力，都应同步评估成本、审核、客服和版本管理，而不能只评估“模型能不能生成”。

## 8. 可复用的内容包规范：用最小 schema 约束事件、随机和叙事

**统一内容 schema 比共享 UI 组件更重要。** 以下示例可用于贯穿事件池、规则引擎和叙事模板。它明确区分 `effects` 与 `narrative`，保证即使 LLM 停止服务，数值结算仍可完成。

```yaml
id: event.qixue.mountain.001
title_key: qixue.mountain.title
version: 1.0.0
tags: [open_world, early_realm, adventure]

weight_table:
  base: 100
  modifiers:
    - when: player.realm >= 3
      multiply: 0.4

requires:
  any:
    - player.realm: [1, 2]
    - player.has_item: fire_charm

choices:
  - id: investigate
    label_key: choice.investigate
    effects:
      - add_resource: { key: lingstone, min: 10, max: 30 }
      - roll_table: loot.early_mountain
    next: event.qixue.mountain.002
  - id: retreat
    label_key: choice.retreat
    effects:
      - add_buff: { key: calm_mind, duration_ticks: 60 }

narrative:
  pool:
    - key: qixue.mountain.001.a
      variables: { npc_role: [采药人, 散修], item: [玉简, 灵石] }
  ai:
    enabled: false
    prompt_ref: flavour.qixue
    max_chars: 90
```

建议配套以下工程机制：

- CI 校验 YAML schema、ID 唯一性和循环引用；
- 数值平衡测试覆盖最小、平均和最大路径；
- 分支测试确保每条 `next` 都存在；
- 叙事文本进入 i18n 键值管理；
- AI 只能引用已审核的 `prompt_ref`，不能拼接任意系统指令或玩家原始文本；
- 发布系统同时写入内容哈希、规则版本和回滚指针。

这一规范的价值不在于限制创作者，而在于让内容、数值和 AI 可以独立发布。否则，一次文本修改可能意外改变概率，一次模型升级也可能影响已上线事件。

## 9. 最终决策：将 AI 作为可降级层，将规则作为不可降级层

**自研产品应采用“规则优先、内容驱动、AI 可选”的组合架构。** 具体来说：

- 采用万界道友明确主张的“AI 文本、规则校验”边界 [1]；
- 借鉴文字修仙模拟器的短局轮回和几分钟单局 [3]；
- 采用灵界的服务端随机、长线循环和版本管理机制 [4]；
- 复用“我的文字修仙全靠刷”的数据驱动前端思路 [5][6]；
- 吸收 Evennia 和 Ranvier 的服务端状态、命令、bundle、skill、effect 和 quest 建模 [8][9]；
- 仅将 AIDungeon 作为开放叙事的上限参照，不作为成本、安全或状态管理范本 [7]。

**最终技术决策可归纳为五条。**

1. **前端：** H5 优先，React/Vite 或 Vue/Pinia 均可；小程序通过 Taro、uni-app 或原生适配。是否跨端应根据团队能力和目标平台决定，而不是默认引入最重方案。
2. **后端：** 首期采用微信云开发，后期根据需要迁移到 CloudBase 云托管或独立 Go/Node 服务。云函数负责登录、存档、随机、结算、交易、审核和模型网关；JSON 数据库与 Postgres 可随复杂度升级。
3. **配置：** 公共内容采用版本化 CDN；私有存档采用服务端数据库；数值、概率和事件配置支持热更；所有状态写入带规则版本和事件日志。
4. **AI：** 默认使用模板库与变量组合，仅对少量高价值文本调用模型。采用白名单意图、结构化输出、缓存、超时、重试、降级和内容安全四层拦截。
5. **合规：** 先以固定选项和非公开测试验证玩法；公开上线前确认小程序主体、深度合成类目、算法备案或第三方合作材料、AI 标识、输入输出审核及未成年人流程。

**最危险的反模式是让 LLM 同时充当规则、叙事和客服。** 更稳健的判断标准是：

> 如果关闭 LLM，玩家是否仍能正常修炼、突破、死亡、重开并获得正确奖励？  
> 如果模型返回任意 JSON，规则引擎是否会拒绝超出边界的奖励？  
> 如果同一操作重放 100 次，服务端是否始终产生可审计结果？  
> 如果生成内容出现风险，是否能按版本和模板立即停用？

只有四项均为“是”，AI 才是增强层，而不是单点故障。

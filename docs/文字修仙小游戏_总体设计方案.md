# 《一念千世》文字修仙小游戏 · 总体项目设计方案

> 定位：**可切换修炼体系的轻 Roguelike 文字修仙**——一局一世，5–8 分钟，1–4 个选项，随时中断随时续，重开即转世。
> 平台：**微信小程序 + H5 网页**（同一套规则核心，两套视图层）。
> 本版目标：**不做执行层面的完善，只做设计与资源层面的极尽完善**，把后续构造资源库所需的全部规格、口径与清单一次性定死。
> 文档版本：v1.0（设计态） · 日期：2026-09

---

## 0. 一页纸总览

| 项 | 结论 |
|---|---|
| 一句话 | 抽命格、选体系、走一世：把网文里"奇遇—抉择—突破—代价"的爽点压缩成一局 5–8 分钟、可无限重开的文字修仙。 |
| 核心循环 | 转世 → 命格/天赋 → 事件流（1–4 选项）→ 修为/资源/因果变化 → 突破或道陨 → 结局 → 元进度沉淀 → 下一世 |
| 单局时长 | 目标 5–8 分钟（快进模式 3 分钟，深度模式 15 分钟），20–30 个事件节点 |
| 单局 LLM 调用 | 首发设计值 **0–3 次**（仅结局卷轴、罕见奇遇、玩家自定义命名），95% 文本来自模板库 |
| 首发体系包 | 6 个（凡人流 / 天才流 / 肉身纪元流 / 诡秘序列流 / 逆天长线流 / 苟道稳健流） |
| 首发事件量 | 母题 ≥ 32，实例化事件 ≥ 1200 条，单局去重后可玩 3 个月不重样 |
| 架构 | `game-core`（纯 TS 规则核心）+ `content`（版本化配置 CDN）+ 云函数规则服务 + 三层文本引擎（模板/缓存 LLM/实时 LLM） |
| 稳定性底线 | **数值永不由模型决定**：模型只填 flavor，规则引擎独占状态层；所有结算可回放 |

## 1. 需求解码与设计目标

把你这一轮的要求拆成可验收的设计目标，并把每一条都翻译成设计约束：

| 你的要求 | 设计翻译 | 验收口径 |
|---|---|---|
| 自由度相对较高 | 三层自由：**体系自由**（换世界包）、**构筑自由**（命格×天赋×词条×因果）、**抉择自由**（事件多分支且改变长期变量） | 每个事件至少改写 1 个长期变量；≥5 套可感知构筑；体系可热切换且资产可迁移 |
| 修炼体系可切换（起点/纵横/番茄） | `World Pack` 插件化：统一内部数值骨架 + 术语词典替换 + 失败方式替换 | 新增一个体系包 = 新增 3 个配置文件（realms / terms / motifs-weight），不动引擎代码 |
| 总结主角配角奇遇作为自由度参考 | 建立「奇遇母题库」：从 24 部作品抽象 32 个母题，实例化时绑定人物/地点/宝物/势力参数 | 母题全部可跨体系复用；同一母题在不同体系下风险类型不同 |
| 每一局快速完成 | 一世制 + 时间压缩（修炼以"年"为单位跳跃）+ 快进/自动 | 首局 ≤5 分钟；30 秒内出现第一次命运变化 |
| 事件选项丰富（1–4 皆可） | 选项数动态 1–4（多数 3），带风险标签与模糊概率提示 | 1 选项=命运已定（演出型），2=抉择型，3=标准，4=高信息量场面 |
| 稳定性 | 规则/随机/存档服务端权威；模型旁路；三级降级 | 模型全挂时游戏可完整通关；断网可玩本地局 |
| 轻松性 | 零教程、零下载、可中断、可跳过、无强制等待 | 首次进入 15 秒内可操作；无定时打卡压力 |
| 游戏性 | 短局 + 元进度 + 构筑 + 图鉴 + 结局评价 | 次日留存靠"再开一世看不同结局"，长期靠图鉴/命格解锁 |
| 小程序 + 网页 | 一套 `game-core` + 两个壳 | 存档互通（同账号），UI 自适应 |
| 简单动画与 UI | 水墨国风 + 轻量 CSS 动效 + 可选音效 | 主包 ≤2MB，低端机自动降级动效 |
| 本轮只要 plan，探索极尽完善 | 本文给出全部资源库规格与规模目标 | 后续可按第 10 章清单直接批量构造资源 |

### 1.1 四条设计铁律

1. **规则独占状态层，模型只碰表达层。** 任何"获得 X 灵石""突破成功"必须由服务端规则算出并落日志，模型输出的文本若含数值，一律当作装饰性文案并强制剥离 [citation:3]。
2. **自由度必须伴随约束。** 每新增一种自由（自由输入、自由交易、自由命名），必须同时新增一层校验、审核与降级，否则自由会转化为事故与成本。
3. **短局必须有沉淀。** 重开不是清空，而是把本局转化为元进度（命格解锁、图鉴、结局评星、因果遗产）。
4. **体系是皮肤，结构是骨架。** 换体系只换术语、资源名、失败方式、奇遇偏好；不换 PowerIndex 曲线、事件调度器与结算公式。

## 2. 参考项目对比验证（7 个样本）

对比目的不是抄，而是确认我们每一处设计取舍在业界已有验证或已有教训。

| 项目 | 形态/开放度 | 技术栈 | 内容组织 | AI 定位 | 稳定/轻松/游戏/自由（5 分制，研究判断） | 对我们的结论 |
|---|---|---|---|---|---|---|
| **万界道友** daoyou.org | 网页，GPL-3.0 开源 | Hono4+Bun / React19+Vite / Postgres+Drizzle，另含 Redis、NATS | 宗门/功法/造物/副本/坊市模块化 | AI 仅做文本、命名、事件描述与奇遇表达；核心数值、资源、奖励、状态仍走规则校验 [citation:3] | 5/3/4/5 | **最值得学的一条**：把 AI 明确钉在表达层。可做我们"模型旁路"的样板 |
| **文字修仙模拟器** vibesims.com/xiuxian | 网页，闭源 | 未披露 | 随机转世、抽天赋、分属性、人生事件流 | 未披露 | 5/5/3/4 | **单局结构样板**：转世—童年—奇遇—突破—意外—封号，几分钟一世。我们直接采用其"一世制"外壳，补上元进度 |
| **灵界 LingVerse** ling.muge.info | 网页，内测 | 未披露 | 境界/地图奇遇/回合斗法/洞府灵田/坊市/宗门/灵宠 | 未使用 LLM（业务随机走服务端安全随机）[citation:1] | 5/3/5/4 | **长线与可信随机样板**；也提示我们：长线 MMO 型内容量压力极大，不做 |
| **我的文字修仙全靠刷** github.com/setube/vue-xiuxiangame | 开源，MIT | Vue + Pinia + Vite | 境界/装备/战斗/资源/修炼前端工程化 | 无 | 5/4/4/3 | **前端工程化与配置结构参考**；也提醒：纯前端存档不可用于正式商业版 |
| **AIDungeon** | 开源，历史版本 | Python + GPT-2 微调 | 自由文本动作 → 树状故事 | 模型全权生成 | 2/4/3/5 | **反面教材**：自由输入带来幻觉、越狱、内容安全、成本四重风险。我们只在"彩蛋/自定义命名"里开一条窄缝 |
| **Evennia** | 开源 MUD 框架 | Python，SQLite/Postgres | 实体—属性—命令—事件建模 | 无内置 | 5/2/5/4 | 吸收其**服务端权威状态**与实体建模思想，不采用其技术栈 |
| **Ranvier MUD** | 开源 Node 引擎 | Node.js，bundle 化 | `areas/items/rooms/npcs/quests/skills/effects` 分 bundle | 无内置 | 5/2/4/4 | 直接借鉴其 **bundle 内容包结构**与热扩展思路，用于我们的 Pack 体系 |

### 2.1 从对比中得到的六条硬结论

1. **"AI 生成剧情"不是卖点，"AI 不破坏剧情"才是。** 万界道友官网把这条写进了公开说明 [citation:3]，说明它已是同类产品的共识边界。
2. **几分钟一世的结构已被验证可行**（文字修仙模拟器 [citation:2]），但必须叠加跨局解锁才能留住人。
3. **服务端权威随机是可信度底线**（灵界 [citation:1]）。客户端掷骰上报结果 = 外挂直通车。
4. **纯前端开源修仙项目适合抄结构，不适合抄架构**：MIT 项目的配置组织值得学，但其本地存档无法支撑跨端与反作弊。
5. **自由输入的代价极高**（AIDungeon）：除非内容安全与成本预算到位，否则不开放。
6. **内容包要 bundle 化**（Ranvier）：体系包、地图包、事件包各自独立、可灰度、可回滚，这是我们"可切换体系"的工程基础。

## 3. 核心体验：一局一世的结构设计

### 3.1 单局时间轴（一世）

```
[0:00] 转世抽命格   —— 出身 + 3 天赋 + 1 缺陷 + 体系包选择（可"随机"一键）
[0:20] 童年期        —— 1–2 个节点，定资质/家世/第一枚伏笔 flag
[1:00] 入门期        —— 3–5 个节点，入宗/散修/旁门，拿到第一个金手指或第一个仇家
[2:30] 成长期        —— 8–12 个节点，修炼—突破—历练循环，资源与因果同步累积
[4:30] 转折期        —— 3–5 个节点，大奇遇 / 大背叛 / 大追杀（张力峰值）
[6:00] 终局          —— 1 个节点 + 结局卷轴（飞升/坐化/隐居/称尊/道陨/成谜）
[6:30] 结算与转世    —— 评星、图鉴入库、元进度沉淀、一键"再入轮回"
```

**节奏控制参数（Tension Curve）**：每个节点带 `tension` 值（0–10），调度器按"低—中—高—回落—峰值"曲线取样，避免一路平淡或一路高压。

### 3.2 快速完成的五个机制

| 机制 | 说明 |
|---|---|
| 时间跳跃 | 修炼不逐日点击，而是"闭关三年 → 一次性结算修为 + 1 个闭关小事件" |
| 快进/自动 | 自动模式 0.8 秒/节点，随时点停；打字机可跳过 |
| 决策密度控制 | 平均每 3 个节点才有 1 个"重大抉择"，其余为轻量反馈 |
| 断点续玩 | 任意节点退出即存，回来从该节点继续（本地快照 + 云端可信存档双写） |
| 无等待设计 | 没有任何"请 2 小时后回来"；离线收益只用于元进度，不阻断主线 |

### 3.3 选项设计规格（1–4 选项）

**选项数量触发规则：**

| 选项数 | 使用场景 | 体验作用 |
|---|---|---|
| 1 | 命运已定（天降横祸、传承灌顶、寿元耗尽） | 演出与推进，制造"身不由己" |
| 2 | 两难（保命 vs 夺宝、正道 vs 魔道） | 强抉择、高记忆点 |
| 3 | 标准节点（激进 / 稳健 / 放弃） | 主力形态，约 55% 节点 |
| 4 | 高信息量场面（拍卖会、宗门大比、阵营站队、诡秘仪式） | 稀有，约 15%，用于制造"大师兄级"名场面 |

**每个选项必须包含：**

```jsonc
{
  "id": "opt_b",
  "text": "以三年苦修换取筑基丹一炉，闭死关",
  "risk_tier": "稳 | 常 | 险 | 狠 | 绝",        // 风险五档，UI 用颜色区分
  "odds_hint": "十拿九稳 | 有把握 | 未卜 | 凶险 | 九死一生", // 模糊概率，不显示精确数字
  "cost_hint": "3 年寿元 / 灵石 200",            // 代价预览，可为空
  "intent": "steady_cultivate",                  // 意图标签：供 AI 与埋点使用
  "requires": { "realm_idx": ">=2", "not_flag": ["cursed"] },
  "outcomes": [ /* 见 5.4 结果倾向表 */ ]
}
```

**差异化原则**：四个选项不能是"收益 10/20/30/40"的线性排列，而应分别改写不同的**长期变量**：

| 选项原型 | 主要改写 | 典型后果 |
|---|---|---|
| 激进（狠） | 战力↑、暴露度↑、因果债务↑ | 短期爽，后期被追杀 |
| 稳健（稳） | 资源↑、修为稳步↑、节奏慢 | 苟到后期，怕"强制事件" |
| 智取（谋） | 信息↑、机缘质量↑、消耗神识/心性 | 低风险高回报，但受属性门槛限制 |
| 放弃（退） | 无事发生、气运↓/心性↑ | 保留实力，可能错过窗口期 |
| 邪（魔道） | 收益极高、业力↑、阵营仇恨↑ | 开启魔道线，触发清算事件 |

## 4. 修炼体系切换系统（World Pack）

### 4.1 三层 Pack 结构

```
World Pack（体系包）   —— 境界序列、术语词典、资源名、失败方式、奇遇偏好权重
   ├── Region Pack（地图包）—— 区域、势力、NPC、准入境界
   └── Event Pack（事件包）—— 母题实例、叙事模板、选项与结果倾向
```

切换体系 = 换 World Pack + 重新权重化 Event Pack，**Region Pack 可混搭**（例如"凡人流境界 + 诡秘流地图"作为高难融合赛季）。

### 4.2 统一数值骨架（内部真相层）

引擎不存"斗帝""序列 5"这类表层名，只存 `power_index`（0–1000）：

| PowerIndex | 通用层 | 通用资源槽 |
|---|---|---|
| 0–10 | 凡俗 | 体力、铜钱、乡里声望 |
| 10–50 | 入门 | 通用货币（灵石/金币）、基础材料 |
| 50–120 | 中坚 | 稀有材料、势力声望 |
| 120–250 | 高层 | 灵脉/法则碎片/权限 |
| 250–450 | 巨头 | 世界权限、阵营令牌 |
| 450–700 | 顶层 | 源质/天道权限 |
| 700–1000 | 超脱 | 不可直视的真相（结局层） |

**统一资源槽（跨体系可折算）：**

| 槽位 | 含义 | 凡人包 | 斗破包 | 诡秘包 | 星空包 |
|---|---|---|---|---|---|
| `currency` | 通用货币 | 灵石 | 金币 | 镑 | 星币 |
| `power` | 修炼能量 | 灵力 | 斗气 | 灵性 | 原能 |
| `rare_mat` | 突破材料 | 灵药/丹 | 魔核/异火 | 非凡特性 | 法则结晶 |
| `favor` | 阵营货币 | 宗门贡献 | 势力人情 | 教会功勋 | 文明积分 |
| `debt` | 因果债务 | 因果/业力 | 血仇 | 聚合仇恨 | 文明债 |
| `corruption` | 污染槽（可选加载） | 心魔 | 焚身异火侵蚀 | 失控值 | 规则反噬 |

**关键设计**：`corruption` 是**可加载模块**。仙侠包默认不加载，诡秘包/道诡包强制加载。切换体系时污染值不自动清零，而是按映射表折算（凡人流的"心魔"→ 诡秘流的"失控倾向"）。

### 4.3 六维属性（跨体系共用）

| 属性 | 作用 | 影响 |
|---|---|---|
| 根骨 | 肉身与战力基数 | 战力、寿元、渡劫存活 |
| 悟性 | 修炼速度与功法上限 | 修为增益、突破成功率 |
| 心性 | 抗心魔/抗污染 | corruption 抗性、强制事件豁免 |
| 气运 | 奇遇质量与稀有事件权重 | 事件池抽样权重、保底 pity |
| 机敏 | 事件成功率与信息获取 | 智取类选项成功率、识破陷阱 |
| 魅力 | 人际关系与道侣/师徒 | 结交道侣、招募、说服 |

派生：`战力 = f(根骨, power_index, 功法, 法宝词条)`，`寿元 = base(realm) × (1 + 根骨/200)`。

### 4.4 首发 6 个体系包（推荐）

以下境界序列取自公开资料核验结果，游戏内建议做**术语去 IP 化处理**（见第 13 章合规）。

|---|---|---|---|---|---|---|
| 1 | `mortal` 凡人流 | 慢热经营 | 炼气→筑基→结丹→元婴→化神→炼虚→合体→大乘→渡劫→真仙→金仙→大罗（12 级） | 催熟灵药的神秘小瓶 | `time_skip`（闭关跳跃）、`alchemy` | 资源断档、被夺宝追杀 |

### 4.6 切换与资产迁移规则

- **可迁移**：元进度、图鉴、解锁命格、奇遇权限、成就、结局收藏。
- **折算迁移**（按 0.6–0.8 折旧）：货币、材料、阵营声望。
- **不迁移但转化**：因果债务 → 新体系的仇恨槽；污染 → 新体系的失控/心魔槽。
- **锁定**：本局内的境界、功法、法宝绑定当前体系；跨局切换体系时按 `power_index` 折算到新体系最近档位（向下取整）。

**融合玩法（赛季制）**：主包 70% + 副包 30%。例：`mortal × mystery` —— 神秘小瓶可催熟灵药，但服用需过 `sanity` 检定；`genius × devour` —— 异火映射为高能源质，但不自动获得不朽神力。

### 5.3 从"随机奖励"升级为"得到—暴露—偿还"

每个高价值奇遇都按三段式设计，这是让事件有记忆点的关键：

```
得到（Get）    —— 获得宝物/功法/身份/情报
暴露（Expose） —— 同时写入暴露度、因果债务、聚合仇恨、阵营怀疑
偿还（Pay）    —— 后续 N 个节点内必然触发清算事件（追杀/夺舍/心魔/天劫/审查）
```

例：拿到神秘小瓶 → 写入 `expose+2, debt+1` → 第 8–15 节点间必触发一次"夺宝追杀"或"师门审查"。

### 5.4 结果倾向表（四段式）

| 段位 | 触发概率带 | 文案语气 | 典型效果 |
|---|---|---|---|
| 大成功 crit | 5–10% | "天道酬勤，竟有意外之喜" | 双倍收益 + 解锁隐藏后续 + 图鉴稀有条目 |
| 成功 success | 45–55% | "有惊无险" | 标准收益 + 1 个长期变量轻微变化 |
| 失败 fail | 25–35% | "事与愿违" | 无收益或小损失 + 负面 flag |
| 大失败 crit_fail | 10–15% | "道心蒙尘" | 重伤/损失/债务/污染 + 强制后续事件 |

**伪随机保底（Pity）**：连续 2 次 fail 后，crit/success 权重 +30%；气运属性提高 crit 上限。避免玩家因连续厄运弃局，同时保留"倒霉也很有戏"的叙事价值。

### 5.5 事件调度算法

```
输入：玩家状态 S、阶段 stage、历史节点 H、体系包 P、气运 L
1. 过滤：requires 条件 + 冷却去重（same_motif / same_npc / same_tag）+ once_per_run
2. 权重：w = base_weight × pack_pref(P) × stage_pref(stage) × luck_factor(L) × tension_fit(当前曲线目标)
3. 保底：若关键事件（金手指/转折/清算）在窗口内未出现，强制提升其权重至必出
4. 抽样：加权无放回抽样（种子来自服务端）
5. 连锁：结算后按 followups 条件入队
6. 收尾：节点耗尽或寿元/生命归零 → 终局
```

**服务端随机证明**：`seed = hash(run_id, node_index, nonce)`，结算日志保存 seed 与结果，可在争议时复算 [citation:1]。

## 7. 规则引擎与结算（稳定性核心）

### 7.1 权威流程

```
客户端动作（option_id / action）
  → 网关：鉴权 + 幂等键（run_id + node_index） + 版本校验（rule_version / content_version）
  → 规则引擎：条件校验 → 服务端 RNG（seed） → 计算 delta → 封顶/下限

  → 返回：{ delta, new_state, next_node_preview, request_id }

```

```jsonc
}
```

重放/补偿：按事件流重算，比对哈希定位分歧。跨端合并以服务端版本号 + 操作日志为准，不使用"最后写入者获胜" [citation:9]。

### 7.3 平衡参数外置

所有曲线与概率放 `balance` 配置层，支持热更与灰度：

| 参数 | 说明 | 首发建议值 |
|---|---|---|
| `cultivate_gain_base` | 每次闭关修为增益基数 | 100 × (1 + 悟性/100) |
| `breakthrough_success` | 突破成功率 | 0.6 + 悟性×0.002 − 境界×0.01 |
| `crit_base` | 大成功率 | 0.07 + 气运×0.001 |
| `crit_fail_base` | 大失败率 | 0.12 − 心性×0.0008 |
| `debt_decay` | 因果债务自然衰减 | 每 5 节点 −1 |
| `pity_bonus` | 连续失败补偿 | +0.3/次，最多叠 2 层 |
| `lifespan_base(realm)` | 各境界寿元 | 按体系包配置 |

## 8. 内部模型（LLM）调用架构

### 8.1 定位：模型是"受约束的内容函数"，不是 GM

```
玩家动作 → 意图映射（白名单）→ 规则引擎结算 → 结构化结果
                                        ↓
                          文本引擎（三层，可全部关闭）
                                        ↓
                          内容安全过滤 → 客户端渲染
```

模型**永不**直接产出数值；若模型文本中出现数字/资源词，进入前先经"数值剥离器"正则清除或降级为模板文本 [citation:3]。

### 8.2 文本三层引擎（L0–L3）

| 层 | 内容 | 延迟预算 | 占比目标 | 成本 |
|---|---|---|---|---|
| L0 静态 | 规则文本、提示、失败语、教程 | <50ms | 40% | 0 |
| L1 模板组合 | 变量槽填充（人物/地点/宝物/天气/境界） | <200ms | **50%** | 0 |
| L2 缓存 LLM | 预生成 + 审核入库的候选文本池 | <300ms | 8% | 摊销 |
| L3 实时 LLM | 结局卷轴、罕见奇遇、自定义命名 | 流式 1–3s | 2% | 高 |

**首发设计值：单局调用 L3 仅 0–3 次**（结局 1 次 + 罕见奇遇 0–1 次 + 可选命名 1 次）。这样即使全量 LLM 不可用，游戏依然完整可玩。

### 8.3 模型路由（Model Router）

| 用途 | 模型档位 | 候选（可替换） | 选型维度 |
|---|---|---|---|
| 意图分类 / 实体抽取（若开放输入） | 小模型 0.5B–7B 或规则优先 | 本地小模型 / 云端轻量档 | 延迟 <300ms、JSON 稳定 |
| 文本安全与合规打标 | 小模型 + 敏感词库 | 云平台内容安全 API + 词库 | 召回率优先 |
| 叙事生成（L2/L3） | 中等通用模型 | 国内主流通用大模型（混元 / DeepSeek / Qwen / GLM 等，按当期评测选择） | 中文古风语感、JSON 稳定性、P95 延迟、单价、并发配额、备案支持 |
| 兜底 | 无模型 | 纯模板 | 100% 可用 |

**抽象层设计**：`ModelProvider` 接口（chat / stream / classify），配置化切换供应商与档位，禁止业务代码硬编码模型名。这样模型升级、比价、灾备都是改配置。

### 8.4 结构化输出契约（强制）

```jsonc
{
  "title": "雾锁寒潭",                       // ≤8 字
  "lines": ["……", "……", "……"],              // 3 段，每段 ≤60 字，总 ≤180 字
  "mood": "eerie | heroic | somber | comic | mystic",
  "tags": ["cave", "goldfinger"],
  "forbidden_check_passed": true,            // 自检：不含数值/资源词/外链/联系方式
  "safety": { "level": "safe", "hits": [] }
}
```

生成约束：使用 Function Calling / JSON Schema 强制结构；长度硬截断；禁止词表（灵石、修为、境界、成功率、外链、现实品牌、联系方式）；温度 0.7–0.9；重复惩罚；超时 3s 重试 1 次后降级。

### 8.5 三级缓存

```
Key = hash(evt_id, band, realm_bucket, faction_tier, pack_id, mood_hint)
1. 模板池命中（L1）→ 直接返回
2. 缓存池命中（L2，预生成 + 人工抽检入库）→ 返回
3. 未命中 → 调模型 → 异步落盘 → 抽检通过后进入 L2 池
```

缓存轻度扰动（同义替换 1 个变量），避免重复感；玩家级去重：同一玩家 30 节点内不重复看到同一条生成文本。

### 8.6 三级降级

| 级别 | 触发 | 表现 |
|---|---|---|
| 一级 | 模型超时/报错/JSON 非法 | 换用 L2 同 key 备用文本 |
| 二级 | L2 也没有 | 用 L1 模板组合生成极简文本 |
| 三级 | 模板也异常 | 只显示状态变化（"修为 +120"），无剧情文本，游戏继续 |

**流式输出只用于非结算文本**：不能在流式中承诺资源，也不能在玩家已看到奖励后撤回。

### 8.7 成本与容量预算（首发估算口径）

| 项 | 假设 | 结果 |
|---|---|---|
| DAU | 10,000 | — |
| 人均局数/日 | 3 局 | 30,000 局/日 |
| L3 调用/局 | ≤3 次 | ≤90,000 次/日 |
| 单次 token | 输入 ~700 / 输出 ~250 | ~85M token/日（需靠缓存压到 ≤15M） |
| 缓存命中目标 | ≥80% | 实际模型调用 ≤18,000 次/日 |

**成本控制闸门**：每账号每日 AI 生成次数上限、全局 QPS 熔断、按量预算告警（日消耗达 80% 自动切 L1）。

### 8.8 可观测性（每次调用必记）

`prompt_token / completion_token / model_version / latency / cache_hit / safety_hits / retry / evt_id / run_id / 最终展示率`；按事件池与玩家分群统计：文本展示率、跳过率、负反馈率、重开率、留存差异。没这些指标就无法判断 AI 是否真在改善体验。

## 9. 前后端技术架构

### 9.1 模块划分（一个核心，两个壳）

```
repo/
├── packages/
│   ├── game-core/        # 纯 TS，无 DOM/无小程序 API/无 LLM SDK
│   │   ├── engine/       # 状态机、结算、RNG 接口、事件调度器
│   │   ├── rules/        # 战斗、突破、突破检定、因果清算
│   │   ├── schema/       # 全部资源库的 Zod/JSON Schema 定义
│   │   └── save/         # 快照序列化、事件流、合并策略
│   ├── content/          # 版本化配置（packs/events/items/narrative/balance）
│   ├── ui-kit/           # 设计系统：水墨组件、动效、字体、色彩变量
│   ├── app-h5/           # React + Vite（或 Vue3）
│   └── app-mp/           # Taro（React 同构）或 uni-app（Vue 同构）
├── server/
│   ├── cloudfunc/        # 云函数：run/turn/save/meta/ai-text
│   └── rule-service/     # 后期可迁 Node/Go 容器化规则服务
└── tools/
    ├── content-lint/     # 内容校验、死链检测、权重体检
    └── gen-narrative/    # 离线批量生成 + 审核入库工具
```

### 9.2 跨端选型对比

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **Taro（React 同构）** | 与 H5 共用 React 心智与 hooks；一份逻辑多端 | 小程序包体与运行时开销；部分原生能力需插件 | 团队 React 背景 → 选它 |
| **uni-app（Vue 同构）** | Vue 生态成熟，插件市场丰富 | 调试链略长 | 团队 Vue 背景 → 选它 |
| **小程序原生 + H5 独立** | 包体最小、性能最好 | 两套 UI 需维护 | 仅小程序单平台且追求极致性能时选 |
| **H5 内嵌小程序 webview** | 一套代码 | 审核与体验风险高，加载慢 | 不推荐 |

**结论**：`game-core` 必须纯 TS 且零平台依赖；视图层按团队技术栈二选一；若只有小程序一个目标且团队熟悉原生，不必为技术潮流引入抽象。

### 9.3 后端：云开发起步 → 容器化演进

| 能力 | 首期（微信云开发/CloudBase） | 演进 |
|---|---|---|
| 登录 | 云开发鉴权（微信/匿名/手机号） | 多端统一账号 |
| 存档 | 云数据库（JSON 文档） | Postgres |
| 玩法计算 | 云函数（无状态、幂等） | Node/Go 规则服务 |
| 配置 | 对象存储 + CDN（版本化 manifest） | 配置中心 + 灰度 |
| AI | 单一云函数代理 | Agent 网关 + 缓存 + 降级 |
| 排行/社交 | 云函数 + 数据库 | 独立服务 |

**读写边界**：客户端只读公开配置与自己存档；所有结算、掉落、突破、交易、签到、排行提交走云函数。CloudBase 提供 HTTP API，可让 H5 复用同一后端，但网页端鉴权与域名策略需单独设计。

### 9.4 API 契约（简化）

| 接口 | 入参 | 出参 |
|---|---|---|
| `POST /run/start` | pack_id, origin, traits, seed_opt | run_id, 首个节点 |
| `POST /turn/submit` | run_id, node_index, option_id, idempotency_key | delta, new_state, next_node, request_id |
| `GET /run/resume` | run_id | snapshot + summary + 当前节点 |
| `POST /run/end` | run_id | 结局卷轴（可含 L3 文本）、评星、元进度增量 |
| `GET /content/manifest` | — | 各包版本与 hash，客户端做差异下载 |
| `POST /ai/flavor` | evt_id, band, context_slot | 文本（可 202 异步 + 轮询/推送） |

幂等：所有写接口带 `idempotency_key = run_id + node_index`，重复提交返回首次结果，杜绝双击刷收益。

### 9.5 内容分发

```
manifest.json（版本、hash、分包列表）
  → 客户端比对本地缓存 → 只下载差异包 → 校验 hash → 载入
```

- 公开内容（境界/事件/物品/模板）CDN 化，全部玩家共享版本；
- 私有状态（存档/排行/交易）服务端持久化；
- 配置分三层：`content`（可热更）/ `balance`（受控灰度）/ `narrative`（模板或 AI 填充）；
- 每个事件带 `version` 与 `rule_ref`，出问题可按版本回滚而不必改数据库。

- 动效统一走 CSS 关键帧，避免重 canvas；粒子 ≤30；
- 低端机检测（帧率采样 3 秒）→ 自动关闭粒子、缩短打字机、降级插画为 CSS 背景；
- 无障碍：字号三档、对比度达标、动效开关（respect prefers-reduced-motion）。

## 12. 稳定性与工程质量

| 维度 | 措施 |
|---|---|
| 幂等 | 所有写接口 `idempotency_key`；重复提交返回首次结果 |
| 超时 | 规则结算 800ms、L3 文本 3s（重试 1 次后降级） |
| 降级 | 三级降级（见 8.6）；模型全挂 → 纯模板可完整通关 |
| 断网 | 本地快照继续单局，恢复后按服务端日志合并；离线局标记不计排行 |
| 防作弊 | 客户端只提交 `option_id`，不提交结果；RNG 服务端；异常频率与收益偏差检测 |
| 版本兼容 | 内容/规则版本号随存档；跨版本回放兼容或强制转世 |
| 灰度 | 按 `pack / content_version / model / 用户分群` 四维灰度，可一键回滚 |
| 监控 | 接口成功率、P95 延迟、结算失败率、AI 调用失败率与成本、单局完成率、崩溃率 |
| 应急 | 按 `tenant + model + template + version` 立即停用的开关 |

## 13. 合规与 IP 风险（必须前置处理）

### 13.1 AIGC 合规（国内硬要求）

- **标识义务**：《人工智能生成合成内容标识办法》自 2025-09-01 施行，AI 生成内容需在合理位置显著标识，并在文件元数据中添加属性信息 [citation:22]；微信/抖音等平台已要求小程序补充"深度合成"类目并在页面显著位置标注"AI 生成" [citation:24][citation:11]。
  → 落地：AI 文本区固定角标「AI 生成」，设置页提供说明与开关，保留生成日志（模型、版本、时间）。
- **算法备案与安全评估**：自研或第三方深度合成服务需相应备案材料与协议；上线前须按当期规则复核 [citation:15][citation:19]。
  → 落地：首发以模板文本为主（L0/L1），把 AI 定位为可选增强，可显著降低备案与审核压力。
- **内容安全三层过滤**：客户端长度/频率/敏感词 → 服务端模型厂商与云平台审核 → 业务规则拦截（禁联系方式、外链、未成年人不当内容）→ 抽检 + 举报闭环 [citation:15]。
- **未成年人**：实名/防沉迷按平台规则；AI 高风险场景仅向成年实名用户开放；限制每日生成次数。
- **隐私**：昵称、存档用于模型上下文前先脱敏并取得授权；不展示 prompt 与其他玩家信息。
- **游戏资质**：带内购或广告的小程序游戏涉及类目与资质要求，需在立项时确认（这属于经营合规，需以最新平台规则与法务意见为准）。

### 13.2 IP 与版权（体系包的红线）

**原则：借鉴"规则与结构"，不使用"独创表达"。**

| 风险项 | 处理 |
|---|---|
| 境界层级名（炼气/筑基/金丹…） | 属通用修仙设定，风险低，可保留（且各体系通用） |
| 作品独有名词（掌天瓶、异火榜、骨文、塔罗会、序列途径名…） | **首发全部替换为原创同义词**；仅在"致敬模式"（可选 DLC/UGC）中经改写后使用 |
| 人物名、招式名、地名 | 100% 原创，走命名库生成并做撞名检测 |
| 情节复述 | 只保留母题骨架（"山洞得宝""被退婚立誓"），不复制具体桥段与台词 |
| UGC 体系编辑器（后期） | 需 UGC 审核机制，且不得允许用户导入原著名词 |

**推荐做法**：把小说体系做成"**风格模板**"（节奏、风险结构、金手指原型），而非法条照搬；首发 6 包命名为原创体系名（如「青冥仙途」「炎武纪元」「太古遗蜕」…），在设置或图鉴中以"灵感来源"方式做风格致谢。

## 14. 数据埋点与平衡验证

**核心指标**：

| 层 | 指标 |
|---|---|
| 获客 | 首次进入耗时、首局完成率、分享率 |
| 体验 | 单局时长分布（目标 5–8 分钟）、节点跳出点、选项分布均匀度、跳过率 |
| 留存 | 次日/7 日留存、人均局数、图鉴完成度增速 |
| AI | L3 调用率、缓存命中率、降级率、文本展示率、P95 延迟、日成本 |
| 平衡 | 各境界流失曲线、结局分布、各体系包胜率差、build 多样性指数 |

**平衡验证方法**：用 `game-core` 在 Node 中跑**蒙特卡洛模拟 10 万局**（无 UI），输出：结局分布、平均局时长、各境界死亡率、资源通胀曲线、build 多样性。所有 balance 改动必须先过模拟再灰度。

**每个阶段都应产出对应的资源库增量**，而不是先做功能后补内容。

## 16. 待你决策的开放问题（下一轮可定）

1. **首发体系包数量**：6 个（推荐）还是精简到 3 个做深？
2. **AI 定位**：保守（仅结局 + 罕见奇遇，0–3 次/局，推荐）还是激进（每节点实时生成）？

7. **商业化**：广告激励（增抽卡次数/跳过）＋外观（不影响数值），还是纯免费？
